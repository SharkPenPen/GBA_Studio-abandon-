# GBA 显示模式对比与本工程选型

> 这份文档回答一个问题：**GBA 的 6 种显示模式（模式 0~5），本工程该用哪种？**
> 结论先放前面：**现在用的模式 3 是对的，但它在"程序画的地图"上很吃亏；
> 更好的做法是"按玩法切模式"** —— 详见最后一节。

---

> **实现进度**（P11/P12）：模式 **0 / 1 / 3 / 4 已验证可用** ✓；
> 模式 **2 做不到**（没有普通图块层，图块画布依赖它）；
> 模式 5 未测（它是 160×128 的小屏，游戏按 240×160 设计）。
> 带 * 的"已实现"指：图块模式靠一张 256 色调色板把画面转成图块，
> 文字和照片都能显示，但**照片会出色斑**（通用调色板配照片的必然结果），
> 地图和 UI 这类平色内容完全没问题。

## 一、先把硬件事实摆清楚

### 1.1 GBA 的 6 种显示模式

| 模式 | 背景层 | 每层色深 | 分辨率 | 特点 |
|---|---|---|---|---|
| **0** | BG0~BG3（4 层，都是图块） | BG0/BG1 可用 4bpp 或 8bpp；BG2/BG3 只能 4bpp | 240×160 | 层数最多，**没有**旋转缩放 |
| **1** | BG0、BG1（图块）+ BG2（仿射） | 同上（仿射层 4/8bpp） | 240×160 | 最常用的"2 图块 + 1 旋转"组合 |
| **2** | BG2、BG3（**只能仿射**） | 4/8bpp | 240×160 | 两层都能旋转缩放，没有普通图块层 |
| **3** | BG2（**位图**，16bpp 直接色） | 32768 色 | 240×160 | 无需调色板，**只有一层、单缓冲** |
| **4** | BG2（**位图**，8bpp） | 256 色 + 调色板 | 240×160 | 有**两个页面**可以翻页（双缓冲） |
| **5** | BG2（**位图**，16bpp） | 32768 色 | **160×128** | 分辨率更小，单缓冲 |

> 注：模式 6/7 是 GBC 和 NDS 上的，GBA 没有。

### 1.2 三条容易被忽略、但决定选型的规则

**规则 1：位图和图块层不能混用。** ✗

模式 0/1/2 给你图块层（硬件滚动、硬件合成），**没有**位图层；
模式 3/4/5 给你一块位图，**没有**图块层。
不存在"背景用图块、文字用位图"这种混搭。

**规则 2：OBJ（硬件精灵）在**所有**模式里都能用。** ✅

这一条最容易被漏掉。精灵是独立于背景层的另一套硬件：
128 个精灵、每行最多 32 个、支持 4bpp/8bpp、支持旋转缩放、**任何模式下都工作**。

但有个坑：**在位图模式下 OBJ 的图块显存只有 16 KB**（0x06014000~0x06017FFF），
因为下面那块 0x06000000~0x06012BFF 被位图占了。
（模式 0/1/2 下 OBJ 有完整的 32 KB。）

16 KB 的 4bpp 图块 = 512 个 8×8 图块；一个 32×32 的精灵占 16 个
→ 还能放 32 个这么大的精灵。**对绝大多数游戏够用。**

**规则 3：显存是 96 KB，按用途切开。**

```
0x06000000 ┬ BG 图块数据 / 位图     64 KB   ← 位图模式下一个屏幕就吃掉 75 KB？见下
0x06010000 ┼ OBJ 图块数据           32 KB   （位图模式下缩到 16 KB）
0x06018000 ┴ 调色板                  1 KB   （BG 512 B + OBJ 512 B，各 256 色）
```

**这里有个必须说清的账**：模式 3 的 240×160×16bpp = **76,800 字节**，
而 BG 区只有 **64 KB** ✗ —— 看起来放不下？

放得下，因为模式 3/4/5 的位图**借用** OBJ 图块区的前半段：
位图实际占 0x06000000~0x06012BFF（76,800 B），OBJ 图块被挤到 0x06014000 之后
（只剩 16 KB）。**这就是"模式 3 没有双缓冲"的根因** ——
96 KB 装不下第二块 76,800 B 的画布。

## 二、本工程现在依赖什么

先把需求列清楚，选型才有依据。逐条看现在的实现：

| 需求 | 现在怎么做的 | 对显示模式的要求 |
|---|---|---|
| **中文点阵文字** | `text.c`：自写 254 字 × 11×11 点阵，逐像素写进位图 | **必须能画位图**（图块是 8×8 网格，见 §3.2）|
| **照片级背景**（1920×1080 缩到 240×160） | 16bpp 直接色全屏位图，一张 75 KB | 位图模式（或接受 256 色，见 §3.1）|
| **立绘**（111×120 等，带透明） | 软件 blit + 特定颜色当透明 key | 位图或 OBJ 都行 |
| **关卡地图**（15×10 图块） | **软件填色**：进关卡时把 150 个 16×16 方块画进位图 | 图块层最合适（现在是硬凑）|
| **地图滚动** | **没做**（软件重画整屏代价太高）| 图块层几乎免费 |
| **音频** | Direct Sound A/B + **DMA1/DMA2** | 与显示模式无关 |

> 顺带一条：音频用的是 DMA1/DMA2，**DMA3 留给图形搬运**（`gfx.c` 的整屏填充/贴图）。
> 这是**设计上的分工**（不是硬件强制），好处是音频 DMA 不会被一次大贴图卡住。
> 换显示模式不影响这个分工。

### 2.1 现在的实际体积（换算成调色板方案要用的数字）

```
ROM 总大小            496.8 KB
  背景 4 张           300.0 KB      ← 16bpp 直接色，一张 75 KB
  立绘+精灵 8 张      167.1 KB
  字库（254 字）        6.4 KB      ← 11×11 点阵，1 位/像素
一张 240×160 16bpp     75.0 KB
一张 240×160 8bpp      37.5 KB      ← 模式 4 的代价：颜色降到 256 色
```

## 三、逐模式对着需求打分

| | 模式 0 | 模式 1 | 模式 2 | **模式 3（现用）** | 模式 4 | 模式 5 |
|---|---|---|---|---|---|---|
| 中文文字（11px 混排） | ✅ 已实现* | ✅ 已实现* | ❌ 未实现 | ✅ **直接画** | ✅ 可以 | ✅ 可以 |
| 照片背景（原色） | ✗ 要转图块 | ✗ | ✗ | ✅ **原色** | ✗ 256 色 | ✅ 原色 |
| 图块地图 + 滚动 | ✅ **最好** | ✅ | ✅ | ✗ 软件填色 | ✗ | ✗ |
| 硬件精灵（OBJ） | ✅ 32 KB | ✅ | ✅ | ⚠ 只有 16 KB | ⚠ 16 KB | ⚠ 16 KB |
| 旋转缩放（背景） | ✗ | ✅ BG2 | ✅ BG2/BG3 | ✗ | ✗ | ✗ |
| 双缓冲（不撕裂） | ✅（图块改写）| ✅ | ✅ | ✗ **做不到** | ✅ 翻页 | ✗ |
| 颜色数 | 256（4bpp）/256（8bpp 单层）| 同左 | 同左 | **32768** | 256 | 32768 |
| 分辨率 | 240×160 | 240×160 | 240×160 | 240×160 | 240×160 | 160×128 |

### 3.1 为什么"照片背景"这一条几乎一票否决模式 0/1/2

我们的背景是 1920×1080 的照片缩到 240×160。
模式 0/1/2 要把一屏画面变成图块：

- 屏幕 = 30×20 = **600 个 8×8 格子**。4bpp 每图块 32 字节 → 600 个 = **19.2 KB**
  → 图块数量**放得下**（BG 区一共 64 KB）✗ 所以**卡住的不是数量**。
- **卡住的是色深**：4bpp = 每个图块只能用 16 色，整层调色板 256 色。
  照片缩到 256 色，渐变天空和海面泡沫会出色带 —— 这正是 `docs/05` 排除模式 4 的同一个理由。
- 另外 600 个图块意味着"每个格子内容都不一样"，等于把图块层**当位图用**：
  既没省显存，也不再能靠"少量图块拼大面积"来省事。

结论：**照片背景配图块层是错配。** 照片要么留在位图模式，
要么先做成"像素画 / 有限色"的美术（那是另一个美术方向，不是显示模式能解决的）。

### 3.2 为什么"中文文字"这一条也几乎一票否决模式 0/1/2

图块是 **8×8 的固定网格**，而我们的文字是：

```
汉字 11×11 像素 + ASCII 半角 6 像素，混排、按像素对齐
```

- 想把每个汉字做成图块：一个字跨 2×2 格 = 4 个图块（16×16），254 个字 = **1016 个图块 = 32.5 KB**
  显存**放得下**（BG 区 64 KB），但——
- **排版被锁进 8 像素网格** ✗：11 像素的字塞进 8 像素的格子，要么缩放变形、要么对不齐。
  这是"能不能做"和"做出来好不好看"的区别，而 galgame 的全部内容就是文字。

真要硬做，业界做法是：在 RAM 里维护一小块"文字位图"，
只把**变化过的 8×8 单元**转成图块传进去（一条 232×36 的对话框约 145 个图块）。
可行，但是**多了一整套缓存/脏标记/回传逻辑**，而收益只是"文字"，不划算。

### 3.3 模式 4 看起来很美（能双缓冲），但代价正好打在我们的软肋上

模式 4 = 8bpp 位图 + 两个页面 → **能翻页，画面不撕裂**，这确实是模式 3 最大的缺点。

但 8bpp 意味着**背景 + 立绘 + 文字全都要挤进同一个 256 色调色板** ✗。
我们的背景是照片，256 色会明显劣化（渐变天空、海面泡沫会出色带）。
`docs/05` 当初就是这么排除它的。

顺带：模式 4 的位图也是**一块**（两个页面各 37.5 KB = 75 KB），
**照样没有图块层**，所以"地图滚动"照样没解决。

---

## 四、关键结论（三条）

1. **位图 vs 图块，二选一，不能混。** 想要图块地图的滚动，就得放弃位图文字。
2. **模式 3 的短板只有两个**：不能双缓冲（撕裂）、程序画的地图要靠软件填色（不能滚动）。
   它的长板（原色照片 + 任意文字排版）正好是这个项目最依赖的两件事。
3. **OBJ 在所有模式都能用** —— 这一条意味着：
   **关卡里的角色/敌人现在就可以改成硬件精灵，不必换显示模式。**
   模式 3 下有 16 KB OBJ 图块（512 个 8×8），够放 30 多个 32×32 的角色。

## 五、可选方案与建议

### 方案 A：维持模式 3，把能吃到的便宜吃掉（**推荐先做这个**）

不动显示模式，只做两件"低风险高收益"的事：

| 做什么 | 收益 | 改动量 |
|---|---|---|
| 关卡的角色/敌人改用 **OBJ 硬件精灵** | CPU 不再逐像素贴角色；能做几十个 | ~150 行（`obj.c`：图块上传 + OAM 写 + 调色板）|
| 地图滚动：**整屏拷贝 + 补新的一列** | 关卡能真滚动（现在完全没有）| ~80 行 |

**关于"位图怎么滚动"，这里必须说清**（第一版我写错了）：

- 位图模式**没有** BG 的滚动寄存器可用（那是给图块层的）✗
  所以滚动 = 把画面整体搬 N 个像素，再把新露出来的一条画上 ✓
- 整屏 76,800 字节，用 DMA3 按 32 位搬 = **19,200 次传输 ≈ 2 万周期** ✓
  一帧有 280,896 周期 → **只占约 7%** ✓✓ 完全做得动
- 所以"模式 3 下也能滚动"，代价是每帧多花 7% 的 CPU（图块层是 0%）✓

**能到什么程度**：地图平滑滚动、几十个角色不掉帧。
代价：地图仍是软件画的，每次滚动多搬 76.8 KB（图块层是硬件做，一分钱不花）。

### 方案 B：按玩法切显示模式（**推荐作为下一步**）

GBA 允许**运行时改显示模式**（写 `REG_DISPCNT` 的 mode 位），
所以可以让不同的玩法用各自合适的模式：

```
剧情模式  →  模式 3   位图：中文文字 + 照片背景（现在的做法，一行不改）
   ↓ 切换时淡出 + 清屏（本来就要清）
关卡模式  →  模式 0   BG0 图块地图 + BG1 装饰 + OBJ 角色；滚动由硬件做
```

| | |
|---|---|
| **收益** | 关卡地图变成硬件图层：滚动几乎免费、地图数据从 75 KB 位图降到几 KB 图块 + 地图 |
| **代价** | 一套图块工具链（图片 → 图块集 + 调色板 + 地图，Python 写，不用 grit）+ 关卡 HUD 文字要么做成图块字要么砍掉 |
| **改动量** | ~350 行：`tile.c`（图块集/地图/调色板加载）+ 关卡改用图块层 + 模式切换的淡出清屏 + 编辑器的图块素材类型 |
| **风险** | 中。两个渲染路径要各自测试；好处是**互不干扰**（剧情路径一行不用改）|

### 方案 C：整个引擎改用模式 1/2（图块 + 仿射）

除非要做"旋转缩放的背景"（比如过场动画、伪 3D），否则**不建议**：
中文文字这一关过不去（见 §3.2），除非接受"文字变丑"或"另写一套图块文字系统"。

### 方案 D：改用模式 4（8bpp + 双缓冲）

**不建议**。它没解决图块问题，还把照片背景降成 256 色 —— 为了"不撕裂"付出的代价太大。
撕裂问题更适合用"淡出/淡入"掩盖（切场景时本来就要淡）。

---

## 六、如果只记一句话

> **模式 3 保住了"文字"和"照片"这两件 galgame 最要紧的事；
> 想补"地图滚动"，正确的路不是换掉模式 3，而是让关卡单独用模式 0（方案 B）。**
>
> 而在那之前，**方案 A 的两件事（OBJ 精灵、脏矩形滚动）性价比最高** ——
> 不动架构就能让关卡真正"能玩起来"。

## 附：本工程相关的其他硬限制（备查）

| 项 | 数值 | 影响 |
|---|---|---|
| CPU | ARM7TDMI @ 16.78 MHz | 软件填色 150 个 16×16 方块 ≈ 一个 VBlank 的量级，能做但不能每帧做 |
| 一帧 | 280,896 周期（≈ 60 fps） | 每帧能搬的像素有上限，这是"整屏重画"不可行的原因 |
| 卡带 ROM | ≤ 32 MB | 现在用了 497 KB，**空间完全不紧张**（所以不必为了省字节做精灵表）|
| EWRAM / IWRAM | 256 KB / 32 KB | 想把整屏背景缓存到 RAM 里做双缓冲：76.8 KB，EWRAM 装得下（但 DMA 到显存仍需一帧时间）|
| 调色板 | BG 256 + OBJ 256 | 两者**独立**，所以"角色用调色板、背景用位图"这种混搭是可能的 |
