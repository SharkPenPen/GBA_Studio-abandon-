# 15 · 底层框架审查：够简洁吗？能扩展成"所有类型"吗？

这份文档回答两个问题，结论都基于**实际代码规模**，不是设想：

1. 现在的框架**简单简洁**吗？
2. 它能**扩展成 GBA 上所有类型游戏**的开发基础吗？

---

## 一、现状盘点

### 引擎侧（C，共约 1260 行）

| 模块 | 行数 | 职责 | 通用性 |
|---|---|---|---|
| `text.c` | 233 | UTF-8 解码 + 二分查字库 + 禁则换行 | ✅ **通用**，任何中文游戏都要 |
| `sound.c` | 186 | Direct Sound A/B + DMA | ✅ **通用** |
| `gfx.c` | 158 | 位图填充/矩形/透明 blit/DMA | ✅ **通用**（但只有模式 3 位图） |
| `console.c` | 108 | ASCII 调试文字 | ✅ 通用 |
| `galgame.c` | 538 | 状态机 / 对话框 / 立绘 / 选项 / 菜单 | ❌ **galgame 专用** |
| `main.c` | 38 | 主循环（vsync + 按键 + update） | 🟡 太薄，没有游戏级抽象 |

### 编辑器侧（Python）

| 部分 | 通用性 |
|---|---|
| `ui/`（主窗口、时间轴、属性生成、对话框） | ✅ **通用**，和游戏类型无关 |
| `modes/` 模式注册表 | ✅ **通用**（加类型 = 加一个模块） |
| `core/assets.py` 素材扫描/导入/归类/合规检查 | ✅ 通用 |
| `core/compiler.py` 时间轴 → 剧本 | 🟡 **VN 形状**（按轨道+片段编译） |
| `core/preview.py` 240×160 渲染 | 🟡 和引擎布局绑定（这是特性，不是缺陷） |
| `core/project.py` 数据模型 | 🟡 有通用骨架，但只被 VN 用例撑起来过 |
| `core/gba_build.py` 工具链封装 | ✅ 通用 |

### 数据模型：通用骨架 vs 实际使用

`class Track / Clip / GObject / Scene / Project` ——
`GObject`（位置/图层/属性字典）**明显是给关卡、精灵、实体准备的**，
但现在**一次都没被用过**（`Scene.objects` 永远是空的）。

也就是说：**通用骨架画出来了，但只有一条腿踩在地上。**

---

## 二、简洁性评估：好

| 指标 | 实测 | 评价 |
|---|---|---|
| C 引擎总行数 | ~1260 行 | ✅ 小。一个下午能通读 |
| 第三方依赖 | libtonc 一个 | ✅ 少 |
| 构建时间 | 2.9 秒 | ✅ 快 |
| 编辑器源码 | ~14 万字节 | ✅ 单人可维护 |
| 层数 | 3 层（引擎 / 数据模型 / 界面） | ✅ 清楚 |
| 每次改动的验证成本 | `python tests\run_all.py` 7.2 秒 | ✅ 低 |

**结论：简洁性没问题**，主要功劳是"不预先造用不上的东西"。

---

## 三、扩展性评估：编辑器可以，引擎不行

逐个游戏类型看**现在能不能做**：

| 类型 | 现在 | 缺什么 |
|---|---|---|
| **galgame / 视觉小说** | ✅ 完整 | — |
| **文字冒险（带分支）** | 🟡 | 引擎已支持 `CMD_CHOICE`，编辑器还不能排分支 |
| **电子小说（带特效）** | 🟡 | `fx` 片段（淡入淡出/震屏）还没实现 |
| **解谜 / 找物** | 🔴 | 光标输入、对象拾取、判定、状态标记 |
| **平台动作** | 🔴 | 图块地图、实体系统、碰撞、精灵帧动画 |
| **RPG** | 🔴 | 地图行走、数值/道具、菜单系统、卡带存档 |
| **弹幕 / 射击** | 🔴 | 大量硬件精灵、碰撞检测、循环滚动背景 |
| **音乐 / 节奏** | 🔴 | 精确时序、音频与画面同步 |

### 缺口清单（按"解锁多少类型"排序）

| # | 缺的能力 | 解锁 | 现在有什么 |
|---|---|---|---|
| 1 | **游戏循环 + 场景栈** | 所有类型 | 一个 `switch (s_state)` |
| 2 | **输入动作映射** | 所有类型 | 直接读 `KEY_A` |
| 3 | **实体/对象系统**（位置、速度、图层、更新） | 动作/RPG/射击/解谜 | 3 个固定立绘槽 |
| 4 | **精灵帧动画** | 动作/RPG | 静态立绘 |
| 5 | **图块地图**（背景层 + 碰撞数据） | 动作/RPG/解谜 | 只有整屏位图 |
| 6 | **剧本变量与条件**（标记位、if） | RPG/解谜/多结局 | 剧本只有线性命令 |
| 7 | **卡带存档** | RPG/所有长篇 | 有菜单入口，没真正写卡带 |
| 8 | **硬件精灵（OBJ）** | 射击/动作 | 全是软件 blit |

> 注意 8 的取舍：P5 算过账，**大尺寸全彩立绘用不了 OBJ**（显存 32KB）。
> 但**小尺寸精灵**（16×16 / 32×32 的角色、子弹）用 OBJ 反而合适 ——
> 这两件事不矛盾，将来是"立绘走软件、小精灵走 OBJ"。

---

## 四、结论

> **编辑器外壳已经是通用的；C 引擎目前是"一个 galgame 引擎"，不是"游戏框架"。**

具体说：

- ✅ **可以留着不动的**：`text.c` / `sound.c` / `gfx.c` / 编辑器的 `ui/`、`modes/`、素材与构建管线
- ⚠️ **需要拆的**：`galgame.c` —— 它把"VN 机制"（对话框/立绘/选项）和"游戏状态机"
  （标题/暂停/消息页）混在 538 行里。前者是**一种游戏类型**，后者是**所有游戏都要的**
- ❌ **需要补的**：游戏循环与场景栈、输入动作映射、实体系统、精灵动画、图块地图、剧本变量

### 最重要的一条判断

**不要现在就去造通用引擎。** 理由：

1. 没有第二种游戏类型的真实需求，造出来的抽象一定是错的
   （P5 那次"要不要上硬件精灵"就是靠算账才没走错）
2. 这个工程最大的资产是**已验证的细节**（中文字库、预览逐像素一致、合规检查、
   硬件限制清单），不是抽象层
3. 每次只加**被真实需求逼出来的**那一层

## 五、建议的演进路线

每一步都**保持 galgame 能跑**（现有测试全程绿灯），不做大爆炸式重构。

### P7 · 拆开单体，抽出通用层（纯重构，不改行为）✅ 已完成

```
source\
  game.c/h      新增：场景栈 + 帧计数                      ← 所有游戏都要
  input.c/h     新增：动作映射（A=确认 可重绑）+ 自动演示   ← 所有游戏都要
  ui.c/h        新增：通用菜单/面板/消息页（带样式表）
  vn.c/h        新增：剧本执行 + 对话框 + 立绘 + 选项
  galgame.c     538 → 283 行：只剩界面状态机 + 接线 + 菜单位置
  gfx.c text.c sound.c   没动
```

验收：`tests\run_all.py` 全绿（10 项）+ ROM 行为一致（见开发日志的对比结果）。

**拆分的边界**（判断标准：换个游戏类型还要不要）：
- `game` / `input` / `ui` —— 要，所以它们不认识 galgame 的任何东西
- `vn` —— 不要，所以它只管"剧情怎么演"，不管"界面怎么切"
- `galgame.c` —— 就是这一种游戏的玩法，新玩法照着它再写一个

### P8 · 关卡模式（验证"多类型"是不是真的）✅ 已完成

先做**最小可玩**：图块地图 + 一个用方向键走的角色 + 碰撞。

结果：**分层成立**。`game` / `input` / `ui` / `gfx` / `text` / `sound` 原样能用，
`vn.c` 一行没碰；编辑器侧加 `modes/level.py` 只改了 `MODES` 表一行。

| 做出来的 | |
|---|---|
| `source/level.c` | 146 行：地图（只画一次）+ 角色 + 四点采样碰撞 |
| `gbastudio/modes/level.py` | 227 行：画笔网格 + 出生点 + 尺寸 |
| `tools/make_project_level.py` | level.txt → C 数组 |

| 暴露的问题 | |
|---|---|
| `input.c` 只有上下、没有左右 | P7 的抽象是照着 VN 的需要做的 —— **早点做第二种玩法就是为了逼出这种偏向** |
| 程序画的地图不能用 `gfx_restore_rect()` | 那个函数是从"背景资源"取像素的，纯代码画的地图没有对应图片 |

还没做：镜头滚动、图块素材（现在是纯色块）、角色精灵。

### P9 · 精灵与动画 ✅ 已完成

动画表（帧序列 + 每帧停几帧）+ 引擎 `anim.c` + 编辑器「精灵」模式
（帧缩略图、顺序可调、**60 帧/秒实时预览**）。关卡里的角色已经换成会动的精灵。

做出来的：

| | |
|---|---|
| `source/anim.c/h` | 约 90 行：播放进度（播到第几帧、还剩几帧换）|
| `gbastudio/modes/sprite.py` | 约 320 行：动画列表 + 帧序列 + 预览 |
| `tools/make_project_anim.py` | 清单里的 animations → `anim_data.c`（平坦数组）|

两个必须解决的新问题：

| 问题 | 处理 |
|---|---|
| 立绘的转换规矩会把 16×24 的帧拉到 120 高 | 新增素材类型「精灵」，**只裁空白、绝不缩放** |
| 精灵下标会被立绘挤走（加句台词动画就错位） | 清单里精灵单独一组，生成时排最前面占 0..N-1 |

还欠：左右翻转贴图、精灵表合并（ROM 放不下再说）。

### P10 · 剧本变量与条件（进行中：已做「剧本切模式」）

已经做完的一半：**剧本里能切换玩法** —— `mode <n>` 命令（编辑器 fx 轨上的
「＋切模式」片段），剧情演到那里进关卡，关卡退出后**回到下一句继续演**。

还没做：`set flag` / `if flag` / 多结局。

### P10b · 剧本变量与条件（原计划）

给剧本加 `set flag` / `if flag` / `jump`，解锁分支与多结局。

### 更远（有真实需求再做）

卡带存档、OBJ 小精灵、音效通道扩展、压缩背景。

---

## 六、明确"现在不做"的事

避免过度设计，这些**先不碰**：

| 不做 | 理由 |
|---|---|
| 通用 ECS 框架 | 没有第二种游戏类型的需求，抽象必错 |
| 字节码 VM（脚本虚拟机） | 现在的固定命令数组对 VN 够用；等 RPG 需要再上 |
| 图块自动转换与压缩 | 现在背景是整屏位图，够用；等内存吃紧再说 |
| 多平台抽象（SDL 之类） | 已经确定只做 GBA（docs/08） |
| 插件系统 | 一个 `MODES` 列表已经够了 |

---

## 七、一句话总结

> **简洁：达标。** 引擎 1260 行、依赖 1 个、构建 3 秒、测试 7 秒。
>
> **扩展性：编辑器达标，引擎差一层。**
> `text/sound/gfx` 可以直接复用；`galgame.c` 需要拆成
> "VN 类型" + "通用游戏层"；实体/地图/动画要按需新增。
>
> **下一步最该做的不是加功能，而是 P7 那次拆分** ——
> 它不改行为、不冒风险，却决定了以后能不能长出第二种游戏类型。
