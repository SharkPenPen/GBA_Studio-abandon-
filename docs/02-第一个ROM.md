# 02 · 一次构建到底发生了什么

这一章把 `.\build.ps1` 拆开讲。看懂之后，你就知道"改代码 → 变成能玩的卡带"
中间到底经过了什么，出问题时也知道该看哪一步。

---

## 一、五个步骤

```
source\main.c  ──①编译──▶  build\main.c.o  ┐
source\sys\*.s ──①编译──▶  build\sys\*.o   ├─②链接─▶ build\gba_ai.elf
.toolchain\lib\libtonc.a ──────────────────┘              │
                                                          ③objcopy
                                                           ▼
                                                     gba_ai.gba
                                                           │
                                                    ④gbafix│⑤check-rom
                                                           ▼
                                                  实机/模拟器可运行的 ROM
```

### ① 编译（CC）：C 代码 → 机器码

每个 `.c` 和 `.s` 单独编译成一个 `.o`（目标文件）。
关键是这几个参数（在 `build.ps1` 里）：

| 参数 | 作用 |
|---|---|
| `-mcpu=arm7tdmi` | 目标 CPU。GBA 用的是 ARM7TDMI，必须明确告诉编译器 |
| `-mtune=arm7tdmi` | 按这个 CPU 做指令调度优化 |
| `-mthumb` | 使用 Thumb 指令集（16 位指令，代码更小，GBA 上更省卡带空间） |
| `-mthumb-interwork` | 允许 Thumb 代码和 ARM 代码互相调用（启动代码是 ARM 模式写的） |
| `-O3` | 优化等级。GBA 只有 16.78 MHz，优化很重要 |
| `-ffunction-sections` `-fdata-sections` | 每个函数/变量单独放一段，配合链接时的 `--gc-sections` 可以把没用到的代码扔掉 |
| `-I .toolchain\libtonc\include` | 告诉编译器去哪找 `tonc.h` |
| `-D__GBA__` | 定义一个宏，让启动代码知道自己在为 GBA 编译 |

### ② 链接（LD）：把一堆 .o 拼成一个程序

链接器做三件事：

1. 把所有 `.o` 和 `libtonc.a`（静态库）、`libc`（newlib）里的代码拼起来；
2. 把函数调用之间的地址填好；
3. **按照链接脚本 `source\sys\gba_cart.ld` 决定每一段放在哪个地址**——
   这是 GBA 编程最核心的一件事，见下面第四节。

产物是 `build\gba_ai.elf`。ELF 里除了机器码，还有符号表、调试信息，
**不能直接当 ROM 用**。

### ③ objcopy：ELF → 纯二进制

```
arm-none-eabi-objcopy -O binary build\gba_ai.elf gba_ai.gba
```

把 ELF 里的"实际内容"抽出来，变成一张连续的二进制镜像。
GBA 卡带里就是这个东西：从 `0x08000000` 开始，一个字节挨一个字节。

### ④ gbafix：修 ROM 头

链接脚本在 ROM 开头预留了 192 字节的头部，但里面**大部分是 0**。
实机 BIOS 开机时会检查：

- `0x04~0x9F`：任天堂 Logo 位图，**不匹配就白屏**；
- `0xBD`：头部校验和，**不对也拒绝启动**。

`tools\gbafix.ps1` 负责把 Logo、固定标记 `0x96`、校验和写进去。
模拟器通常不管这些，但实机很严格——所以这一步不能省。

### ⑤ check-rom：自检

`scripts\check-rom.ps1` 反过来验一遍：Logo 对不对、校验和算出来一致不一致、
标题是不是可见字符、入口是不是一条分支指令。**构建完立刻发现问题**，
比烧到卡带上才发现白屏强得多。

## 二、ROM 里的字节长什么样

编译成功的 ROM，开头 0x100 字节是这样排的：

| 偏移 | 长度 | 内容 | 谁来写 |
|---|---|---|---|
| `0x000` | 4 | `b` 分支指令（跳到 0xC0） | `gba_crt0.s` |
| `0x004` | 156 | 任天堂 Logo 位图 | `gbafix.ps1` |
| `0x0A0` | 12 | 游戏标题（ASCII） | `gbafix.ps1`（来自 `build.ps1` 顶部的 `$GameTitle`） |
| `0x0AC` | 4 | 游戏代码 | `gbafix.ps1`（`$GameCode`） |
| `0x0B0` | 2 | 厂商代码 | `gbafix.ps1`（`$MakerCode`） |
| `0x0B2` | 1 | 固定值 `0x96` | `gbafix.ps1` |
| `0x0B3` | 1 | main unit code（0） | `gbafix.ps1` |
| `0x0B4` | 1 | device type（0） | `gbafix.ps1` |
| `0x0B5` | 7 | 保留 | —— |
| `0x0BC` | 1 | 软件版本 | —— |
| `0x0BD` | 1 | **头部校验和** | `gbafix.ps1` |
| `0x0BE` | 2 | 保留（0） | `gbafix.ps1` |
| `0x0C0` | 4 | 多卡带（multiboot）入口分支 | `gba_crt0.s` |
| `0x0C4` | 28 | multiboot 参数 | `gba_crt0.s` |
| `0x0E0` | 4 | JOYBUS 入口 | `gba_crt0.s` |
| `0x0E4` | … | **真正的启动代码从这里开始** | `gba_crt0.s` |
| 之后 | … | `.text`（你的代码）、`.rodata`（常量） | 编译器 |

看 `source\sys\gba_crt0.s` 的前 20 行，你会发现它就是用汇编一条条"填"出这张表。

## 三、开机后 crt0 干了什么

CPU 上电后从 `0x08000000` 开始执行，经过两个分支跳到 `0x0E4`，
然后 `gba_crt0.s` 按顺序做六件事：

1. **关中断**：往 `0x04000208`（IME 寄存器）写 0，避免初始化到一半被打断；
2. **设置栈指针**：给 IRQ 模式和系统模式各设一个栈（栈在 IWRAM 顶部，和 BIOS 保持一致）；
3. **清空 IWRAM**（32 KB）：全部清零；
4. **把 `.data` 段从 ROM 拷到 RAM**：有初值的全局变量，初值存在 ROM 里，运行时必须搬到 RAM；
5. **清空 EWRAM**（256 KB）并搬运 `.ewram` 段；
6. **调用 `main()`**。

`main()` 返回的话，crt0 会执行 `swi #0x00`（软复位）把机器重启——
所以你的 `main()` 正常写法是一个永不退出的 `while(1)` 循环。

## 四、内存地图：为什么链接脚本要分三个区

GBA 的内存不是一整块，而是几个速度和大小都不同的区域：

| 区域 | 地址 | 大小 | 速度 | 在本工程里放什么 |
|---|---|---|---|---|
| **ROM**（卡带） | `0x08000000` | 最大 32 MB | 慢（等一个等待周期） | 代码 `.text`、常量 `.rodata` |
| **EWRAM**（扩展内存） | `0x02000000` | 256 KB | 慢（16 位总线） | 大块数据（`-ffunction-sections` 之外的大数组） |
| **IWRAM**（内部内存） | `0x03000000` | 32 KB | **快（32 位总线）** | 全局变量 `.data`/`.bss`、**栈** |
| **VRAM**（显存） | `0x06000000` | 96 KB | —— | 画面数据（tile、位图、地图） |
| 调色板 | `0x05000000` | 1 KB | —— | 颜色表 |
| OAM（精灵属性） | `0x07000000` | 1 KB | —— | 128 个精灵的位置/形状 |

链接脚本 `gba_cart.ld` 开头的 `MEMORY { ... }` 块就是这张表：

```
MEMORY {
    ROM     : ORIGIN = 0x08000000, LENGTH = 32M
    IWRAM   : ORIGIN = 0x03000000, LENGTH = 32K
    EWRAM   : ORIGIN = 0x02000000, LENGTH = 256K
}
```

**这是 GBA 编程最需要建立的直觉**：RAM 只有 288 KB（32 KB 快 + 256 KB 慢），
比一张手机照片还小。所以：

- 大数组要显式放进 EWRAM（用 `__attribute__((section(".ewram")))`）；
- 频繁访问的变量放 IWRAM；
- 图片、地图、音乐都是"从 ROM 里读出来，需要时才搬进 VRAM"。

`.\build.ps1` 每次都会打印 `arm-none-eabi-size` 的结果，
`bss` + `data` 就是你的 RAM 占用，**逼近 32 KB 时要注意**。

## 五、`source\main.c` 逐段解读

打开 `source\main.c`，对照下面几段：

### 主循环骨架

```c
while (1) {
    vid_vsync();     // 1. 等下一帧开始（每秒 60 次）
    key_poll();      // 2. 读一次按键
    /* 3. 改数据 */
    /* 4. 只重画"变化了的部分" */
}
```

**所有游戏都是这个骨架**。区别只在于第 3、4 步有多复杂。
`vid_vsync()` 是必须的：不等的话，你会在屏幕刷新到一半时改显存，画面会撕裂。

### ★ 第 4 步为什么是"只重画变化的部分"

这一版的主循环踩过两个真实的坑，值得单独讲——它们都是 GBA 新手最容易撞的墙，
而且报错信息完全帮不上忙（画面不对，但程序不崩）。

#### 坑 1：绘制顺序必须和电子束的扫描顺序一致（自上而下）

GBA 屏幕是从上往下一行行显示的。如果你画完屏幕底部、最后才去画顶部那几行，
这时电子束早就扫过顶部了 —— 这一帧顶部显示不出来，而下一帧开头又被清屏覆盖，
于是表现为**顶部内容完全不显示或疯狂闪烁**。

实际症状：底部那行文字正常，顶部三行一个字都不出现。

**改法**：把绘制代码按屏幕从上到下的顺序排列（顶部文字 → 中部图形 → 底部文字）。

#### 坑 2：一帧只有 280,896 个周期，"每帧重画整屏"根本画不完

`clear_screen()` 看着简单，但它要往 VRAM 写 19,200 次 32 位数据，
而 GBA 的 VRAM 是 16 位总线 —— 实测**光清一次屏就吃掉约 60% 的一帧**。
再加上画边框、画文字，一帧根本不够。

后果和坑 1 叠加：每帧开头清屏，等清完 + 画完，电子束已经跑到屏幕下半部分了，
于是**上半屏永远显示"刚清空、还没来得及画"的状态**（实测：边框只能从第 66 行往下看到）。

**改法不是硬提速，而是改变思路 —— 局部重绘**：

| 内容 | 画几次 |
|---|---|
| 底色、边框、标题、底部操作提示 | **只画一次**（游戏开始前） |
| 主角方块 | 只在移动时：擦掉旧位置 + 画到新位置 |
| 坐标文字 | 只在坐标变化时：擦掉那一行（8 像素高）+ 重写 |

这样每帧真正的工作量只有几十个像素的擦除和几个字形，远小于一帧的预算，画面完全稳定。
`source\main.c` 里用 `prevX / prevY / prevColorIdx` 三个变量记录"上一帧的状态"，
就是用来判断"什么变了"。

> 更彻底的做法是**双缓冲**：在模式 4/5 下准备两个位图层，画完一个再切换显示
> （硬件翻页，完全无撕裂）。等你做到"整屏都在动"的游戏时再用它，
> 见 [docs/04-学习路线.md](04-学习路线.md) 的 M3。

#### 顺便：屏幕文字是怎么通的

`source\console.c` 覆盖了 newlib 的 `_write()`（它在 `source\sys\syscalls.c` 里是
`__attribute__((weak))`，所以能被替换），把 `printf` 的输出转交给 libtonc 的 TTE 画到屏幕上。
另外还必须 `setvbuf(stdout, NULL, _IONBF, 0)`：否则 stdout 是块缓冲，
`printf` 的内容会攒着不输出，屏幕上半天不出现文字。

### 按键的两种问法

```c
if (key_hit(KEY_A))      // 只在"这一帧刚按下"为真 → 适合切换开关、跳一下
if (key_is_down(KEY_A))  // 按住期间一直为真 → 适合持续动作
player.x += key_tri_horz() * 2;   // -1/0/+1 三态 → 适合移动，自带长按重复节奏
```

这也是游戏编程的通用概念：**边沿触发** vs **电平触发**。

### 模式 3 的显存公式

```c
vid_mem[y * 240 + x] = color;   // 第 y 行第 x 列的像素
```

模式 3 是"直接画点"的位图模式，最直观，适合入门。
它的代价是：**没有硬件加速**，每帧都要 CPU 自己把所有像素写一遍，
而且 16 位色下 240×160 就吃掉 76800 字节显存（总共才 96 KB）。

真正的商业游戏用的是**模式 0 + tile（图块）**：把画面拆成 8×8 的小块，
重复的块只存一份，硬件负责拼接。后面学 Tonc 的 "Tile/map" 章节就会讲到。

### 颜色

```c
RGB15(31, 8, 8)   // 红 31、绿 8、蓝 8，每个通道 0~31（5 位）
```

GBA 是 15 位色（BGR555），比 PC 的 24 位色少得多。
所以**颜色过渡会明显有断层**，这是硬件限制，不是 bug。屏幕不发光，实际看着比电脑上暗。

## 六、三个动手练习

改完记得跑 `.\build.ps1 -Run`。这三题分别练"改数值"、"加对象"、"改逻辑"：

**练习 1（改数值）**：让方块移动速度变成每帧 4 像素，尺寸变成 32×32。
> 提示：`player.x += key_tri_horz() * 2;` 里的 `2`，和 `player.size = 16;`。

**练习 2（加对象）**：再加一个方块，用固定颜色，画在屏幕左上角。
> 提示：再声明一个 `Box` 变量，然后在绘制部分多调一次 `fill_rect()`。
> 注意：先画的会被后画的盖住——这就是"图层顺序"。

**练习 3（改逻辑）**：按住 B 键时方块缩小，松开恢复。
> 提示：用 `key_is_down(KEY_B)` 配合 `player.size = 8;` / `16;`。
> 如果发现"按住会疯狂闪烁"，想想为什么——这正好和 `key_hit` 的区别有关。

做完这三题，你就算真正上手了。接下来去读 Tonc 教程（见
[docs/04-学习路线.md](04-学习路线.md)）。
