# GBAStudio.0 —— 方案设计（未实施）

> 本文只定方案，不动代码。看完请拍板第 12 节的 5 个决定。

---

## 1. 一句话结论

把"节点式剧情编辑器"升级成 **Godot 式编辑器（场景树 + 视口 + 属性 + 资源库）+ Scratch 式积木逻辑**，
逻辑编译成**字节码**由 GBA 端的虚拟机执行；作者全程不写代码，
PC 上所见即所得地预览，一键导出 `.gba`。

现有工程的**底层 90% 可以留用**（中文字库、素材转换、ARM 工具链、ROM 头处理），
要重写的是**编辑器外壳**和 **GBA 端的执行内核**。

---

## 2. 你的需求拆成 4 个技术问题

| 你说的 | 本质是什么 | 难度 |
|---|---|---|
| 参考 Godot 2D 的界面 | 一套**多面板 + 视口 + 树形结构 + 属性属性**的编辑器外壳 | 中（有成熟控件，主要是工作量） |
| 尽量不用编程语言 | 程序逻辑要变成**可视化积木**，且能编译成机器能跑的东西 | 高（这是核心难点） |
| 台词/配音/立绘要对应 | **数据模型**问题：角色/素材必须是一张互相关联的表，而不是散落的节点 | 中（设计对了就不复杂） |
| 导出 GBA | 积木 → **字节码** → GBA 上的虚拟机执行 | 高（要写 VM 和音频） |

**这四个问题里，第 2 和第 4 是同一个问题**：积木必须编译成一种中间格式，
而 GBA 端要有一个能执行它的解释器。这个决定定了，其他都好办。

---

## 3. 四个不含糊的判断

### 3.1 「不用编程语言」的边界要说清楚

**你做游戏全程不写代码** —— 这是目标，能达到。
但**工具本身必须用编程语言写**（Python 写编辑器、C 写 GBA 内核）。
这两件事不冲突，但我不想让你误以为"连工具都不用代码"。

类比：Ren'Py、RPG Maker、GDevelop 的作者都不写代码，但引擎是 C++/JS 写的。

### 3.2 借 Godot 的**界面范式**，不是借 Godot

我们要复刻的是它的**交互方式**：

- 左上 **场景树**：这一屏有哪些东西（背景/立绘/对话框），谁盖在谁上面
- 中间 **视口**：240×160 的画布，可以直接拖立绘、调位置，所见即所得
- 右侧 **属性**：选中什么就显示什么属性，改完立刻看到
- 底部 **资源库**：所有图片/音乐/语音，拖进来就能用
- **信号/事件**：点按钮 → 触发一段逻辑

而**不**把 Godot 引擎搬过来（那会变成"用 Godot 做 GBA 游戏"，做不到）。
内核仍然是我们自己的 GBA 运行时。

### 3.3 逻辑用积木，但**必须编译成字节码**，不能直接解释积木

两条路：

| 方案 | 做法 | 问题 |
|---|---|---|
| A. GBA 直接读积木 | 把积木结构塞进 ROM，GBA 现场解释 | 积木结构臃肿（每个积木几十字节），GBA 的 288KB 内存和 16MHz CPU 扛不住 |
| **B. 编译成字节码** ✅ | 编辑器把积木编译成一串紧凑指令（每条 1~6 字节），GBA 跑一个小虚拟机 | 需要写 VM（约 800 行 C），但这是**唯一可行的路**，也是 Ren'Py/Scratch 自己的做法 |

**选 B。** 好处还不止性能：以后加新积木 = 加一条新指令，GBA 端不用重编；
同一份字节码还能在 PC 上跑（做预览和 PC 版）。

### 3.4 现有工程哪些留、哪些换

| 现有东西 | 处置 | 理由 |
|---|---|---|
| `.toolchain`（ARM 编译器 + libtonc） | ✅ 全留 | 干活的就是它 |
| `tools/make_cjk_font.py`（中文点阵字库） | ✅ 全留 | 已解决最难的中文显示问题 |
| `tools/make_assets.py`（素材转换） | 🔧 改造 | 改成"按资源库清单批量转换" |
| `source/text.c`（中文渲染） | ✅ 全留 | UTF-8 + 二分查字 + 禁则换行，都验证过 |
| `source/gfx.c`（位图/透明 blit/DMA） | ✅ 全留 | 底层原语 |
| `source/galgame.c`（写死的状态机） | ❌ 替换 | 改成"场景对象系统 + VM" |
| `scenario.txt` 剧本格式 | 🔧 降级为中间格式 | 变成字节码的文本形态，给人看/调试用 |
| `studio/`（节点编辑器 v1） | 📦 保留归档 | 能用，别删；新版另开目录 |
| `scripts/build-studio.ps1`（打包） | 🔧 改造 | 换 PySide6，加资源打包 |

**结论：不用推倒重来，大概 60% 的底层能直接复用。**

│  │      ...              │        项目文件 project.gbagbastudio          │
│  └────────────────────────┘        （JSON + 素材目录引用）              │
└────────────────────────────┬───────────────────────────────────────────┘
                             │ 导出
                    ┌────────▼────────┐
                    │ 编译器（Python） │  积木 → 字节码；素材 → 二进制资源包
                    └────────┬────────┘
                             │
        ┌────────────────────▼─────────────────────┐
        │  GBA 运行时（C + libtonc，现有工程改造）  │

**关键点：同一份项目数据，两条执行路径**
- PC 预览：Python 版 VM（几毫秒启动，即时看到效果）
- GBA 出货：C 版 VM（同一个指令集）

这是"不写代码也能开发"的前提 —— 不然每次改一句台词都要等 40 秒编译。

## 5. 编辑器设计

### 5.1 界面布局（对齐 Godot）

```
┌──────────────────────────────────────────────────────────────────┐
│ 主菜单   场景 ▾   运行 ▶   导出 GBA   资源 ▾                       │
├──────────┬────────────────────────────────────┬──────────────────┤
│ 场景树    │                                    │ 属性            │
│          │        视口 240×160（3 倍显示）      │                  │
│ ▸ 场景1  │      ┌──────────────────┐          │ 位置 X  [ 120 ]  │
│   ├背景  │      │                  │          │ 位置 Y  [  40 ]  │
│   ├立绘A │      │   海岸 + 魔女     │          │ 缩放   [ 100% ]  │
│   ├立绘B │      │   + 对话框        │          │ 图层   [ 2   ]   │
│   └对话框│      └──────────────────┘          │ 素材   [ 立绘/魔女/笑 ]│
│          │      可拖拽 / 对齐线 / 吸附         │                  │
│ 逻辑列表  │                                    │ ── 动画 ──        │
│  ├序章   │                                    │ 淡入 0.3 秒       │
│  └选项A  │                                    │                  │
├──────────┴────────────────────────────────────┴──────────────────┤
│ 资源库 │ 背景(20) │ 立绘(30) │ 音乐(8) │ 语音(146) │ 字库 │ 角色表   │
└──────────────────────────────────────────────────────────────────┘
```

面板全部可拖动停靠/浮动/合并成标签页（Qt 的 `QDockWidget` 原生支持，Godot 也是这个手感）。

### 5.2 积木逻辑编辑器（Scratch 式）

按类别分色，左侧积木盒，右侧拼接区：

```
【事件】 当剧情开始 / 当选择 [选项一] / 当按下 [A] / 当变量 [好感度] > 5
【演出】 显示背景[B] 以[淡入0.3秒] / 显示立绘[角色] 在[左] 表情[笑] / 隐藏立绘 / 抖动屏幕
【对话】 说话 [角色] 内容[……] 语音[自动] / 旁白 [内容] / 清空对话框
【音频】 播放音乐[BGM] 循环 / 停止音乐 / 播放音效[SE]
【流程】 等待[1]秒 / 等待按键 / 选项 [A]→ / [B]→ / 跳转[章节] / 结束
【控制】 重复[3]次 / 如果…否则 / 等待直到
【数据】 设[好感度]为[0] / 把[好感度]增加[1] / 好感度 （取值）
```

**积木长什么样、有哪些槽位，全部由一张"积木定义表"（JSON）描述** ——
加新积木 = 加一条定义 + 加一条 VM 指令，界面代码不用动。
（这一点沿用现在节点版的做法，那次证明是有效的。）

## 6. 数据模型 —— 专门解决"台词/配音/立绘对应"

你提到的痛点本质是：**同一句台词要同时关联"谁在说、什么表情、放哪段语音"**，
节点式里这三样是散的，所以越做越乱。

解法：**角色表 + 素材命名约定 + 说话积木自动关联**（Ren'Py 就是这么干的）。

### 6.1 角色表（关键设计）

| 字段 | 例子 | 作用 |
|---|---|---|
| 角色 ID | `witch` | 内部标识 |
| 显示名 | 魔女 | 对话框里显示 |
| 名字颜色 | `#ffd166` | 名字行高亮色 |
| 立绘组 | `char/witch/{normal,smile,angry,sad}` | 一组表情 |
| 默认位置 | 左 | |
| **语音前缀** | `voice/witch_` | ⭐ 自动找语音用 |
| 主色 | 绿 | 用于界面标识 |

### 6.2 说话积木怎么写

作者只填两个东西：

```
说话 [魔女 ▾] 内容 [海风停了。]  语音 [自动 ▾]
```

系统自动完成：

- **立绘**：如果这一屏没有魔女的立绘 → 自动按角色表显示；表情默认 `normal`
- **语音**：按"章节名 + 角色ID + 句子序号"去找 `voice/witch_0103.ogg`；
  找不到就**静默跳过**（不报错，方便先写剧本后配音）
- **名字颜色**：自动用角色表里的颜色
- **名字牌**：自动生成，不用手动摆

想手动指定就改下拉框：`语音 [手动 ▾] → [witch_0103]`。
**默认全自动，需要时才手动** —— 这是不让工作量爆炸的关键。

### 6.3 素材命名约定

```
assets/
  bg/      海岸.png  沙漠.png ...
  char/    魔女/normal.png  smile.png ...
           少女/normal.png ...
  bgm/     序章.ogg ...
  se/      点击.ogg ...
  voice/   序章/witch_0101.ogg ...     ← 章节/角色_句子号
```

编辑器按目录自动建角色表和资源库，不用手工登记。
（导入时自动跑现在的 `make_assets.py` 那套：缩放到 240×160、抠透明、转 16 位色）

## 7. GBA 端运行时

### 7.1 场景对象系统（替代写死的状态机）

一个极小的对象模型：

```c
typedef struct {
    u8   type;        // 背景 / 立绘 / 对话框 / 文本 / 图片
    u8   layer;       // 画在第几层（决定覆盖顺序）
    s16  x, y;        // 位置
    u8   visible;
    u8   alpha_mode;  // 无 / 淡入淡出（用抖动模拟）
    u16  asset_id;    // 指向 ROM 里的资源表
    u16  anim;        // 动画状态
} GObj;
```

约 20 个对象就够一屏 galgame 用（20 × 16 字节 = 320 字节 RAM）。

**为什么需要它**：现在 `galgame.c` 把"左边一张立绘、右边一张立绘、底下对话框"写死了。
要支持"三个人同时在场""立绘移动""对话框换个样式"就必须有对象系统。

### 7.2 字节码 VM（草案）

指令定长或半定长，每条 2~6 字节：

```c
enum {
  OP_END,        OP_BG,         OP_CHAR_SHOW,  OP_CHAR_HIDE,
  OP_SAY,        OP_SAY_NOVOICE,OP_CHOICE,     OP_JUMP,
  OP_JUMP_IF,    OP_WAIT,       OP_WAIT_KEY,   OP_SET_VAR,
  OP_ADD_VAR,    OP_CMP,        OP_BGM,        OP_SE,
  OP_VOICE,      OP_FADE,       OP_SCENE,      OP_CALL,
  OP_RET,        OP_SAVE,       OP_LOAD,       OP_RANDOM,
};
```

- 操作数用变长编码（小数值 1 字节，大数值 3 字节）
- 字符串/资源表放在 ROM 里的常量池
- **阻塞型指令**（说话、等待、等待按键）会让 VM 每帧"让出"，由主循环推进
- 存档 = 变量表 + 当前指令指针，序列化到卡带存档区

**规模估计**：VM 核心约 600~900 行 C，加场景系统约 1500 行。
（现有 `galgame.c` 约 600 行，是它的子集）

### 7.3 音频 —— 必须先算清楚账

GBA 的音频硬件：**4 个声道**（2 方波 + 1 波形 + 1 噪声）+ **2 个 DMA PCM 通道**。

| 用途 | 技术方案 | 单条体积 | 数量 | 小计 |
|---|---|---|---|---|
| BGM | 4 声道模块音乐（自制播放器或找开源） | 40 KB / 首（2 分钟） | 10 首 | 400 KB |
| 语音 | 8bit / 11kHz PCM（DMA 播放） | 16 KB / 条（1.5 秒） | 200 条 | 3.2 MB |
| 音效 | 8bit / 11kHz | 2 KB | 60 条 | 120 KB |
| 背景 | 16 位色 240×160 | 76.8 KB | 20 张 | 1.5 MB |
| 立绘 | 16 位色 / 约 120px 高 | 约 30 KB | 30 张（含表情） | 0.9 MB |
| 中文字库 | 点阵 | 100 KB（4500 字） | 1 套 | 100 KB |
| 代码 + 字节码 | | | | 100 KB |
| **合计** | | | | **约 6.3 MB** |

**结论：一部中篇语音 galgame 约 6~7 MB，32MB 的卡带完全装得下。**
但要注意三个硬限制：

1. **语音音质**：8bit/11kHz 听起来像老式电话。想好听要 16bit/22kHz，
   体积 ×4（200 条 → 12.8MB），仍然可行但要克制数量。
2. **不能同时干太多事**：播语音时别做整屏重绘（立绘切换要错开 1~2 帧）
3. **音乐引擎要自己写**：本环境拿不到 maxmod（官方音乐库），
   要么自己写一个简单模块播放器（约 400 行 C），要么找 MIT 协议的开源实现。
   **这是本方案里技术风险最高的一项**，建议放在最后做。

## 8. 作者的一天（工作流）

```
1. 建项目        → 选个文件夹，编辑器自动建 assets/ 目录结构
2. 导素材        → 把 PNG/WAV 拖进资源库窗口，编辑器自动缩放/裁透明/建角色表
3. 搭一屏        → 视口里摆背景、拖两个立绘、调对话框位置（所见即所得）
4. 写逻辑        → 积木区拼：显示背景 → 说话 → 说话 → 选项 → …
5. 点预览 ▶      → 立刻弹出一个 240×160 的小窗口，打字机、选项都能真实点
6. 反复改 3~5    → 每次改完 1 秒内看到效果（不用编译）
7. 导出 GBA      → 编译 + 打包，40 秒出 ROM
8. 真机/模拟器验  → 用现在的 play.cmd / mGBA
```

**第 5 步（PC 即时预览）是整套方案体验的分水岭** ——
没有它，"不写代码"就是空话（改一句台词等 40 秒没人受得了）。

## 9. 技术选型（需要你拍板的第一件事）

编辑器的界面框架，四个选项：

| 方案 | 优点 | 缺点 | 评价 |
|---|---|---|---|
| 继续用 Tkinter（现在这个） | 已有代码、零依赖、打包 10MB | **撑不起**多面板停靠、缩放视口、积木拖拽；观感和性能都差 | ❌ 不适合 |
| **PySide6 / Qt** ✅ | `QDockWidget` 就是 Godot 那种停靠面板；`QGraphicsView` 就是视口和积木画布；界面专业；**能直接复用现有全部 Python 管线** | 打包体积涨到 150~250MB，单文件启动 3~5 秒 | ✅ **推荐** |
| Godot 自己写编辑器 | 界面天生像 Godot | 要用 GDScript 重写全部管线；导出体积 80MB+；本环境调试慢 | ⚠️ 备选 |
| Web（Electron / Tauri） | 界面最灵活漂亮 | 需要 Node + WebView，还要和 Python 编译链通信，链路最长最脆 | ❌ 现阶段不划算 |

**推荐 PySide6。** 核心理由：不浪费已经跑通的那条 Python 编译流水线。
已确认清华镜像有 `PySide6 6.12.0 win_amd64`，国内网络能装。

| **P3** | 资源库 + 角色表 + 素材导入 | 拖 PNG 进来自动建角色/表情；语音自动关联 | ████ |
| **P4** | 积木逻辑编辑器 + 编译器 | 积木 → 字节码；预览里能跑分支和多结局 | █████ |
| **P5** | GBA 端：场景对象系统 + C 版 VM | **积木编出来的剧情在真机/mGBA 上跑起来** | █████ |
| **P6** | 音频（音效 → BGM → 语音） | ROM 里能出声 | ████（风险最高） |
| **P7** | 打磨：存档、backlog、转场、PC 版导出、安装包 | 可发布的制作工具 | ███ |

**里程碑意义**：**P5 完成时，你的"不写代码做 GBA galgame"就真正成立了**；
P6 决定它像不像商业作品。

**P1~P2 是短期能看到的成果**（约相当于现在这个工具 2~3 倍的工作量），
建议先做这两步，用起来觉得顺手再继续。

## 11. 风险与取舍（不粉饰）

| 风险 | 说明 | 对策 |
|---|---|---|
| **体积与启动** | Qt 版单文件 exe 约 150~250MB，启动 3~5 秒 | 或用"文件夹版"（启动快、体积相同）；或接受 |
| **音频引擎** | 官方 maxmod 拿不到，要自己写或找开源 | 放到 P6；先用"无音乐"跑通全流程 |
| **GBA 性能** | 语音 + BGM + 立绘切换同时进行会掉帧 | 播放语音时禁止整屏重绘；错帧处理 |
| **中文点阵字库** | 长篇 4500 字 × 22 字节 ≈ 100KB，可接受；但**无法做字体切换** | 已解决，按剧本生成 |
| **积木表达力** | 纯积木做复杂逻辑（状态机、多结局管理）会很难看 | 提供"章节/标签"跳转 + 变量；复杂逻辑仍可用积木组合表达 |
| **工作量** | 这是重写编辑器，P1~P5 是**数十小时级**的工程量 | 严格按阶段走，每阶段可用 |
| **不可逆** | 换框架后现有 studio/ 不能直接升级 | 新版另开目录（`gbastudio/`），v1 保留可用 |

## 12. 需要你拍板的 5 个决定

1. **界面框架**：用 PySide6（推荐）？还是继续 Tkinter / 或试试 Godot 写编辑器？
2. **exe 体积**：能接受从 10MB 涨到 150~250MB、启动慢到 3~5 秒吗？
   （不接受的话，可以考虑"文件夹版"或 Web 版，但体验/链路各有代价）
3. **语音音质取舍**：
   - A. 8bit/11kHz —— 200 条语音只占 3.2MB，但音质像老式电话
   - B. 16bit/22kHz —— 好听，同样条数要 12.8MB（32MB 卡带仍装得下）
   - C. 先不做语音，只做 BGM + 音效
4. **要不要 PC 版**：同一份工程顺带导出"能在电脑上跑的版本"（工作量增加不多，
   但能让别人不装模拟器就玩到）
5. **第一步做什么**：建议 P1+P2（编辑器骨架 + PC 即时预览），
   因为这两步做完你就能真正"用起来"，判断整套方案顺不顺手

## 13. 追加要求：能不能全用 C？（2026-10 追加）

**答：能，而且有一个我之前没想到的重大好处。** 下面是完整判断。

### 13.1 先澄清一个容易混的地方

| 东西 | 跑在哪 | 现在是什么语言 |
|---|---|---|
| 游戏本体（`.gba` ROM） | **GBA 实机** | **已经是纯 C** ✅ |
| 中文字库生成 / 素材转换 | 你的 PC | Python（要改） |
| 编辑器界面 | 你的 PC | Python + Qt（计划中） |
| 编译打包 | 你的 PC | PowerShell（要改） |

**GBA 那一侧本来就是纯 C，不用动。** 你的 PC 是 Ryzen 9 7900X + Win10，一点都不老 ——
所以"设备老旧"这个理由，只对**最终跑游戏的 GBA** 成立，而它已经是 C 了。

但如果你要的是**别的**（下面 13.5 三种动机），结论可能完全不同，请对号入座。

### 13.2 全 C 真正的技术好处（比我原本想的更好）

**PC 预览和 GBA 可以共用同一份代码。**

```
         ┌──────────────────────────┐
         │  vm.c   （字节码虚拟机）  │
         │  render.c（240×160 渲染） │  ← 同一份源码
         └───────┬──────────┬───────┘
                 │          │
      arm-none-eabi-gcc   mingw-gcc
                 │          │
            ┌────▼───┐  ┌───▼─────────┐
            │ GBA ROM│  │ PC 预览窗口  │
            └────────┘  └─────────────┘
              像素一致、行为一致
```

对比 Python 方案：VM 要写**两遍**（C 版给 GBA、Python 版给预览），
两边行为会慢慢走样 —— "预览里好好的，烧进 ROM 就不对"这种问题会一直折磨你。

**全 C 让预览和实机是同一份代码编出来的，像素级一致。** 这一条的份量很重。

### 13.3 全 C 的代价（说清楚，不粉饰）

| 项目 | Qt 方案 | 全 C（Win32 API） |
|---|---|---|
| 界面观感 | 专业、现代 | 朴素，深色主题要自己画 |
| 可拖动停靠面板 | `QDockWidget` 直接给 | 要自己写（建议先做**固定分区 + 可拖分隔条**） |
| 属性表格 / 积木画布 | 有现成控件基类 | 全靠自己画（GDI 画图不难，但代码量上去） |
| exe 体积 | 150~250 MB | **0.5~2 MB** |
| 依赖 | 打包 Python 运行时 | **零依赖**（静态链接） |
| 启动速度 | 3~5 秒 | **瞬间** |
| 能跑在老 Windows 上 | 基本不行 | **能（XP 及以上）** |
| 我的开发工作量 | 1× | **约 1.5~2×** |
| 便利性 | Python 迭代快、库多 | 手工内存管理、编译-调试循环慢 |

### 13.4 全 C 之后，几个关键环节怎么落地

都不是问题，方案已确认可行：

| 环节 | 全 C 的做法 | 代码量 |
|---|---|---|
| **中文字库**（最要紧） | **用 Windows GDI 渲染**：`TextOut`/`GetGlyphOutline` 在 12px 下同样会命中宋体的内嵌点阵，和现在 Pillow 出来的结果一致 | 约 150 行 |
| 备选字库方案 | 直接解析 TTF 的 `EBDT/EBLC` 点阵表（不缩放、不要 FreeType） | 约 700 行 |
| 素材转换（PNG 解码/缩放/透明） | **stb_image.h**（单文件、公有领域、可直接内嵌） | 约 100 行调用 |
| 项目文件（JSON 读写） | **cJSON** 或 **jsmn**（单文件、MIT） | 约 50 行调用 |
| 界面 | **Win32 API + 通用控件**（TreeView / ListView / Edit / 菜单 / 文件对话框都是系统自带） | 主体工作量 |
| WAV 语音试听 | 自己读 WAV + `waveOut` 播放 | 约 200 行 |
| OGG 音乐试听 | 需要 libvorbis（大）→ **建议编辑器内只试听 WAV**，OGG 交给外部播放器 | — |
| 调用 ARM 工具链编译 | `CreateProcess` 起 `build.ps1` / 直接调 gcc | 约 300 行 |

**Windows C 编译器**：本机目前**没有**（已确认；`arm-none-eabi-gcc` 是交叉编译器，编不了 Windows 程序）。
但我测了 6 个下载渠道，**全部可达** ✅：

| 渠道 | 可达 |
|---|---|
| MSYS2 清华镜像 / 中科大镜像 | ✅ HTTP 200 |
| SourceForge mingw-w64 | ✅ HTTP 200 |
| TDM-GCC 官网 | ✅ HTTP 200 |
| MSVC Build Tools (aka.ms) | ✅ HTTP 200 |
| TCC（1MB 迷你编译器） | ✅ HTTP 200 |

**推荐装 MSYS2（走清华镜像）+ `pacman -S mingw-w64-x86_64-gcc`**，全程国内网络，约 500MB。

### 13.5 请对号入座：你要"全 C"是出于哪种动机？

不同动机，推荐不一样：

| 你的动机 | 推荐 | 说明 |
|---|---|---|
| **A. 最终要移植到别的老平台**（GBA 之外） | ✅ **全 C** | 收益最大：VM/渲染/工具链全都能跟着走 |
| **B. 工具要能在老电脑上跑 / 免安装 U 盘带走** | ✅ **全 C** | 1MB 单 exe、零依赖、XP 都能跑 |
| **C. 不想同时维护两种语言** | ✅ **全 C** | 一种语言、一套构建，长期更省心 |
| D. 以为"编辑器要跑在 GBA 上" | ❌ 这是误会 | 编辑器跑在 PC 上；GBA 端已经是纯 C 了 |

**如果是 A / B / C 中任意一个，我建议就走全 C**，代价（界面朴素些、开发慢一点）
换来的是**零依赖 + 极小体积 + 预览与实机同源**，对这个项目很划算。

如果是 D，那 Qt 方案的开发效率会高很多。

### 13.6 全 C 路线对第 12 节"待拍板项"的修订

| 原问题 | 全 C 下的答案 |
|---|---|
| 1. 界面框架 | **Win32 API（纯 C）**，不用 Qt |
| 2. exe 体积 | 不再是问题：**0.5~2 MB、零依赖、瞬间启动** |
| 3. 语音音质 | 不受影响，仍按原预算（8bit/11kHz ≈ 3.2MB / 200 条） |
| 4. 要不要 PC 版 | **白送**：预览用的就是 PC 运行时代码，加个导出按钮就行 |
| 5. 第一步做什么 | 调整为先做 **P0.5：装 Windows C 编译器 + 跑通"共享 VM/渲染"的最小骨架**（一个能同时编给 GBA 和 PC 的 `render.c`），这是全 C 方案的命门，要先验证 |

**P0.5 是关键**：先用最小代价证明"同一份 C 代码能同时编到 GBA 和 Windows 并显示同样画面"。
这一步通了，全 C 方案就稳了；通不了，及早回头用 Qt，不浪费时间。
