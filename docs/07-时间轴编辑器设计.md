# 时间轴式 galgame 编辑器 —— 设计（未实施）

> 2026-10 追加。用户明确：主界面改成**剪视频式多轨道时间轴**，
> Scratch 积木只用于"逻辑"部分，**整个项目全 C 实现**。
> 本文只定方案。

---

## 1. 结论：这个方向比节点式好，但有一处必须改造

**好在哪**：时间轴天生解决你提的痛点 —— **台词・配音・立绘的对应关系变成"看得见的上下对齐"**，
而不是散落在节点里靠脑子记。

**必须改造哪**：**剪视频的时间是绝对的，galgame 的时间要等玩家。**
如果照搬剪视频的"到点就播"，做出来的就不是 galgame，而是**自动播放的动画片**了 ——
玩家不能停下来看、不能自己控制节奏。

所以要引入**混合时间制**（第 3 节），这是整个方案的关键设计。

---

## 2. 为什么时间轴特别适合"带配音的 galgame"

带语音的 galgame 本质上是**配了画的广播剧**：一句台词对应一段语音，
语音多长台词就该显示多久。这正是剪辑软件最擅长表达的东西。

对比一下同一个需求：

| 需求 | 节点式怎么做 | 时间轴怎么做 |
|---|---|---|
| 这句台词配哪段语音 | 在节点属性里填语音文件名 | 语音片段**就在台词片段正下方**，一眼看到 |
| 这句要显示多久 | 手动填秒数，或写"等语音结束" | 片段宽度**自动等于语音时长**，不用填 |
| 音乐从哪句进 | 在某个节点上挂"播放音乐" | BGM 轨道上直接拖到那句台词上方 |
| 三句话之间插一个音效 | 加一个节点，顺序容易搞错 | 音效轨道上点一下，位置任意精确 |
| 立绘什么时候换表情 | 加立绘节点 | 立绘轨道上切一段，和台词对齐 |
| 语音和语音有没有撞车 | 完全看不出来 | 轨道上直接看到重叠，编辑器还能报警 |

**最后一条很重要**：GBA 只有 2 个 DMA 音频通道，语音重叠是硬错误，
时间轴是唯一能一眼看出来的视图。

## 3. ⚠️ 核心设计：混合时间制（galgame 的时间不是绝对的）

### 3.1 问题

剪视频：时间轴第 10 秒 = 绝对的第 10 秒。
galgame：玩家不按键，第 10 秒永远来不了。

### 3.2 解法：每个片段声明自己的"推进方式"

| 推进方式 | 含义 | 用在哪 | GBA 端怎么实现 |
|---|---|---|---|
| **等按键** | 显示到玩家按 A | 普通对话（默认） | VM 挂起，等按键事件 |
| **等语音结束** | 语音播完自动下一句 | 独白、旁白、自动演示 | 查 DMA 是否播完 |
| **等语音结束或按键** | 语音没完可按掉 | 语音对话最常用 ⭐ | 两个条件或关系 |
| **固定时长** | 比如 1.5 秒 | 演出、过场、特效 | 数帧（60 帧 = 1 秒） |
| **等动画结束** | 淡入淡出播完 | 转场 | 查动画状态 |

**默认用「等按键」，语音片段默认用「等语音结束或按键」。**

### 3.3 那么时间轴上的"时间"是什么？

**是排版视图，不是运行时钟。** 两个含义要说清楚：

1. **片段宽度**：默认按"预计占用时长"画（台词片段 = 对应语音的长度；没语音的按字数估）
   → 目的是让你**看出节奏**、能对齐，不是"到点就播"
2. **两种段落模式**（编译器按这个处理）：

| 段落模式 | 时间轴上的时间 | 编译结果 |
|---|---|---|
| **对话模式**（默认） | 虚拟时间，仅用于对齐 | 逐个片段编译成"等待条件"，后面的时间**顺延** |
| **演出模式**（自动播放） | **真实时间**，严格按秒走 | 编译成定时指令，适合开场动画 / ED / 过场 |

段落模式在时间轴上用一个小的标记区分（对话段落底色浅、演出段落底色深），
一眼能看出"这段是玩家控制节奏的"。

### 3.4 这个设计带来的一个额外好处

**编辑器能算出"这一段大概多久"**：
把所有片段按语音长度加起来 → 显示"本章预计 12 分 30 秒"。
做配音预算、排工期时非常有用。

## 4. 轨道怎么设计

按"从下往上是被覆盖关系"排（和剪辑软件一致，下面的在先画）：

| 轨道 | 图标 | 片段内容 | 片段属性 | 上限 |
|---|---|---|---|---|
| **特效 FX** | ✨ | 淡入淡出 / 震屏 / 闪白 | 类型、时长、强度 | 1 条 |
| **立绘 C** | 👤 | 第三个人物（群像用） | 角色、表情、位置 | 1 条 |
| **立绘 B** | 👤 | 右边人物 | 角色、表情、位置、进场动画 | 1 条 |
| **立绘 A** | 👤 | 左边人物 | 同上 | 1 条 |
| **背景 BG** | 🖼 | 背景切换 | 背景图、切换方式（硬切/淡入） | 1 条 |
| **台词 TXT** | 💬 | 一句对话 / 旁白 | 角色、内容、语音、推进方式、名字牌 | 1 条 |
| **语音 VO** | 🗣 | 一段配音（**显示波形**） | 音频文件、音量 | 1 条 ⚠ 不能重叠 |
| **BGM** | 🎵 | 一段音乐 | 文件、循环、淡入淡出 | 1 条 |
| **音效 SE** | 🔊 | 单个音效（**显示波形**） | 文件、音量 | 多条（可重叠） |

轨道可以增删、静音、锁定；立绘轨道可以加（需要四个人就加一条）。

**为什么立绘要分 3 条而不是 1 条**：分轨道才能让"左右两个人同时在场、
各自换表情"变得直观 —— 这是节点式最乱的地方。

## 6. 配音 / 立绘 / 台词的自动对应

沿用第 6 节（`06` 文档）的角色表设计，时间轴让它更省事：

1. **拖语音进来时**：按文件名 `w0101.ogg` 自动匹配到"第 101 句"的台词片段
   （命名约定见 `06` 文档 6.3），匹配不上就放在语音轨让你手动挪
2. **语音片段自动对齐到台词片段下方**，宽度 = 真实时长
3. **台词片段的"预计时长"自动取语音长度**，不用手填
4. **立绘自动出现**：说话的角色如果不在场，自动在该句开始处插入显示片段
   （可以在属性里关掉"自动立绘"）
5. **缺语音不报错**：先写剧本后配音是常态，缺的语音在轨道上显示为虚框，
   编译时静默跳过

## 7. 分支和章节怎么办（时间轴是线性的）

用剪辑软件的**"序列"**概念（Premiere 的嵌套序列）：

```
主序列          序章 → [选择点] → 汇合 → 终章
                 │
                 ├── 序列: 海岸路线   （一条独立时间轴）
                 └── 序列: 悬崖路线   （另一条独立时间轴）
```

- 时间轴上放一个**"选择"片段**：内容是选项文本 + 目标序列
- 序列可以嵌套、可以跳回（循环）
- 素材库下方的"序列列表"就是章节列表（同时也解决了"长篇怎么分章"）
- **变量和条件**放在积木区（第 8 节），不在时间轴上

## 8. Scratch 积木保留，但退到"逻辑"位置

时间轴解决**演出**（谁在什么时候出现、说什么、配什么音），
积木解决**逻辑**（变量、条件、分支、循环）。

```
积木区（按需展开，不占主界面）
  当 剧情开始        →  播放序列 [序章]
  当 选择[跟上她]    →  设 好感度 +1  →  播放序列 [海岸路线]
  当 变量[好感度] > 3 →  在 [终章] 里解锁 [真结局]
```

两者分工清楚：**画面上的事用时间轴，规则上的事用积木。**
这也是 RPG Maker / GDevelop 的做法。

## 9. 编译模型：时间轴 → 字节码

```
时间轴（人看的）
   │  ① 按轨道收集所有片段
   │  ② 按开始时间归并成一个事件表
   │  ③ 按"推进方式"决定每个事件后面是"等待条件"还是"定时等待"
   ▼
事件表（中间格式，可读文本，方便调试）
   t=0     BG    海岸  fade=30
   t=0     BGM   序章  loop
   t=30    CHAR  A=魔女/笑 左
   t=45    SAY   witch "海风停了。" voice=w0101 wait=VOICE_OR_KEY
   t=?     ...（等按键的片段后面的时间自动顺延）
   ▼
字节码（GBA 跑的东西）
   OP_BG 1 30 | OP_BGM 3 1 | OP_WAIT 30 | OP_CHAR 0 0 1 ...
```

**中间那层"事件表"要保留成文本**，两个用处：
- 出问题时能直接看编译成了什么（和现在"查看剧本"按钮一个作用）
- 以后想手写脚本，可以直接写事件表跳过时间轴

## 10. GBA 端可行性核对

| 问题 | 结论 |
|---|---|
| 时间精度 | 60 帧/秒 → 16.7ms，做 galgame 足够（不需要更高） |
| 语音播放 | DMA PCM（8bit/11kHz），CPU 开销小 |
| 语音长度怎么知道 | 编译时算好写进资源表（字节数 ÷ 采样率） |
| "语音播完没"怎么查 | 查 DMA 剩余计数或双缓冲标志位 |
| 同时几路音频 | **2 个 DMA 通道**：1 路语音 + 1 路音效；BGM 走硬件 4 声道 ✓ |
| 语音重叠 | **硬错误**，编辑器必须报警（时间轴上一眼可见） |
| 淡入淡出 | 模式 3 无硬件混合 → 用**抖动渐变**（亮度分级）实现，已在 `docs/05` 验证思路 |
| 震屏 | 每帧偏移绘制起点，便宜 |
| 立绘进场动画 | 位置插值（几帧内改 x/y），便宜 |

## 11. 全 C（Win32）实现要点 —— 好消息：时间轴比 Godot 式界面**更好写**

我上次说"全 C 的代价是界面开发量 1.5~2 倍"，**时间轴方案把这个代价降下来了**：

| 界面元素 | Godot 式（原方案） | 时间轴（现方案） |
|---|---|---|
| 可拖动停靠面板 | 要自己实现，很麻烦 | **固定分区 + 可拖分隔条**就够了（剪辑软件也是这么分的） |
| 主画布 | 自由缩放的场景视口 + 对齐辅助线 | **矩形网格 + 播放头**，简单得多 |
| 片段交互 | 节点连线、端口命中测试 | **矩形命中测试 + 拖拽 + 吸附**，最基础的操作 |
| 波形显示 | 不需要 | 需要（但只是每列取 min/max，约 80 行） |
| 积木拖拽 | 需要（形状拼接复杂） | **不在主界面**，可以后做 |

**结论**：全 C + 时间轴这个组合，开发量比我上次估计的**低**，
而且 exe 依然是 1~2MB、零依赖、瞬间启动。

技术上要用的东西（都是单文件、许可宽松）：

| 用途 | 用什么 |
|---|---|
| PNG 解码 | `stb_image.h`（公有领域） |
| JSON 读写 | `cJSON` 或 `jsmn`（MIT） |
| 中文字库光栅化 | **Windows GDI**（12px 下命中宋体内嵌点阵，和现在 Pillow 结果一致） |
| WAV 读取 + 试听 | 自己读 + `waveOut` |
| 界面 | Win32 API + 通用控件 + GDI 自绘时间轴 |
| 调 ARM 工具链 | `CreateProcess` |

**Windows C 编译器**：本机没有，但 6 个下载渠道实测全部可达（MSYS2 清华镜像、SourceForge、TDM-GCC、MSVC、TCC）。
推荐 MSYS2 清华镜像 + `pacman -S mingw-w64-x86_64-gcc`，约 500MB，全程国内网络。
