# 多类型游戏目标下的选型（含"类 Godot 编辑器"）

> 2026-10。前提变更：目标从"galgame 专用"扩大到**"类 Godot 的 2D 游戏开发编辑器，galgame 只是其中一个模式"**。
> 本文回答：丙还合适吗？严格按简单简洁，有没有更合适的？

---

## 1. 直接回答：丙不再合适

不是因为 Python/Tkinter 差，而是**"简单"的含义在这个目标下反转了**：

| 目标 | 什么最"简单" |
|---|---|
| 做一个小工具（如节点编辑器、时间轴） | **Tkinter**：零依赖、代码少 |
| 做"多模式通用游戏编辑器" | **手搓编辑器 UI 本身就是最大的复杂来源** |

"类 Godot 编辑器"意味着要自己实现：

- 场景树、属性（这两个还行）
- **视口**：缩放、平移、多选、对齐吸附、缩放手柄、坐标网格
- **资源库**：缩略图、拖放、导入设置
- **图块编辑器**：地图绘制、自动图块、图块集管理
- **精灵/动画编辑器**：帧序列、时间轴、洋葱皮
- **多模式切换**（关卡模式 / 剧情模式 / 精灵模式 / 逻辑模式）
- **撤销重做**（覆盖以上全部操作）
- 停靠面板、快捷键体系、项目设置……

用 Tkinter 手搓这些 ≈ **1 万行以上 UI 代码**，而且随着功能增加会越来越难维护。

**换句话说：丙省下的是"依赖"，付出的是"自己重写一个 Godot 编辑器"。**

---

## 2. 先拆成三件独立的事（不要混在一起决定）

| # | 是什么 | 能不能后换 | 现在该做什么 |
|---|---|---|---|
| 1 | **引擎地基**（GBA 端怎么画东西） | ❌ 换起来最贵 | **现在就做成通用的** |
| 2 | **数据模型**（项目文件格式） | ❌ 换起来贵，还会丢已有作品 | **现在就做成通用的** |
| 3 | **编辑器外壳**（PC 端界面） | ✅ 三层里最便宜 | 可以先简单，以后再换 |

**核心结论：编辑器外壳是最容易换的一层。所以现在不值得为"用哪个 GUI 库"纠结太久，
而应该先把 1 和 2 做对。** 这两件做对了，将来换壳不丢任何东西。

---

## 3. 引擎地基必须升级（最要紧，和编辑器选型无关）

### 3.1 现状的天花板

现在是**模式 3（位图直色）**：

- ✅ 适合 AVG：直色、免调色板、画面好看
- ❌ **做不了动作/RPG/射击**：没有硬件精灵、没有图块滚动，全靠 CPU 逐像素画

**实测教训**（`docs/05` 记录过）：软件 blit 两张 148px 立绘就吃掉约 0.6 帧，直接导致画面撕裂。
这就是模式 3 的天花板 —— 它只够支撑"画面几乎静止"的 AVG。

### 3.2 必须换成通用地基

**模式 0/1（图块）+ 硬件 OBJ 精灵 + 调色板 + 4 层 BG + 硬件滚动 + 实体系统。**

这是所有 GBA 商业游戏的标准做法（口袋妖怪、黄金太阳、马里奥 Advance 都是这套），
一套地基就能覆盖：**AVG / RPG / 平台动作 / 射击 / 解谜**。

### 3.3 galgame 在新地基上怎么做（都能做，有的还更好）

| 元素 | 图块地基上的做法 |
|---|---|
| 背景 | 图块 BG（原图 → 256 色量化 + 抖动，观感接近现在） |
| 立绘 | **硬件 OBJ**（不占 CPU，且支持硬件合成）或大立绘软 blit 到图块层 |
| 文字 | **图块化字符层**：12×12 汉字 = 2×2 个 8×8 图块 = 4 个图块；更新一个字只写 128 字节，比现在逐像素 blit 快得多 |
| 淡入淡出 | **调色板渐变** —— 模式 0 有调色板，这个效果反而比模式 3 **更好做** ✅ |
| 选项菜单 | 图块或 OBJ |

**代价**：`text.c` 从"直接写显存"改成"写图块"（约 200 行），`gfx.c` 增加 OBJ/调色板管理。

**收益**：一套地基通吃所有类型，而且性能余量大得多。

## 4. 编辑器外壳的三个候选

可达性已实测：PySide6 清华镜像 ✅、Godot 官网 ✅、TuxFamily 镜像 ✅。

| | **丙：Tkinter** | **A：Python + Qt** | **B：Godot + 自写导出插件** |
|---|---|---|---|
| 编辑器 UI 代码量 | 最多（1 万行+，易失控） | 中（4~6 千行，控件现成） | **几乎不写**（Godot 本体白送） |
| 新增工具链 | 无 | PySide6（150~250 MB） | Godot 单 exe（免安装） |
| 你的上手难度 | 最低 | 低 | **最高**（Godot 概念多：场景/节点/资源/信号…） |
| 界面能力 | 够用，但会到极限 | 专业 | 专业（就是 Godot） |
| 多模式切换 | 手工搭 | 手工搭 | **白送** |
| 图块/动画编辑器 | 全手搓 | 全手搓 | 大部分白送 |
| GBA 合规检查 | 自己写 | 自己写 | 自己写（插件面板） |
| 所见即所得 | 自己写预览 | 自己写预览 | **打折**：Godot 用 GPU 渲染，真机是量化+抖动 → 必须另做"真机预览窗" |
| 主要风险 | 后期失控 | 工作量 | 依赖 Godot API/版本 |

---

## 5. 我的建议：分两步，不要现在就把目标定成 mini-Godot

### 第一步（现在）

按 galgame 做**时间轴编辑器**（丙的壳），但：

- **引擎地基按第 3 节升级成通用**（图块 + OBJ + 实体）
- **数据模型按通用设计**（场景 / 对象 / 层 / 图块 / 精灵 / 事件表），
  只是当前只实现"剧情模式"用到的那部分

### 第二步（当你要做第二种类型时）

再决定换 A（Qt）还是 B（Godot）。那时你已经知道：

- 自己真正需要哪几种模式
- 哪些功能最常用、哪些是想象出来的需求

因为数据模型是通用的，**换壳不丢任何已完成的作品**。

### 为什么现在不直接上通用编辑器

1. **你已经交过一次学费了**：节点式做出来才发现方向要改。
   这不是错（做工具本来就要迭代），但它说明一件事 ——
   **在没做完一个完整作品之前设计通用编辑器，是在为想象中的需求付钱。**
2. galgame 是"最简单又能跑通全链路"的类型。用它先把
   **编辑 → 编译 → 导出 → 真机**整条链路验证通，风险最低。
3. 通用编辑器的工作量是专用编辑器的 **3~4 倍**。如果方向再调整，浪费更大。

---

## 6. 如果你确定要一步到位（直接做类 Godot 编辑器）

那就选 **B（Godot + 自写 GBA 导出插件）** —— 它是唯一"不用自己写编辑器 UI"的路。

### 6.1 映射关系

| Godot 里的东西 | 变成 GBA 的什么 |
|---|---|
| `TileMapLayer` | GBA 图块层（8×8 图块、4bpp、256 色） |
| `Sprite2D` / `AnimatedSprite2D` | 硬件 OBJ（或软 blit） |
| `AnimationPlayer` | 动画数据 |
| 我自定义的节点 | GBA 对象（背景 / 立绘 / 对话框 / 实体） |
| `AudioStreamPlayer` | 4 声道音乐 / PCM 语音 |

### 6.2 必须自写的三个插件面板

1. **GBA 合规检查**（最重要）：
   调色板超 256 色？图块超 VRAM？精灵超 128 个？ROM 超 32 MB？
   —— 实时报警。**这是这类工具最有价值的部分**，也是 Godot 本身不会告诉你的。
2. **真机预览窗**：用我们的 C 运行时代码渲染 240×160（不是 Godot 的 GPU 画面）。
3. **导出**：转换资源 + 调用 ARM 工具链 + 出 `.gba`。

### 6.3 逻辑层建议用"事件表"而不是 Scratch 积木

对**游戏逻辑**（条件→动作）来说，事件表（Construct / GDevelop 那种）
比积木更简单、更好写、更好读：

```
条件                     动作
按下右键               →  角色向右移动
角色碰到金币           →  金币消失 + 分数+1
分数 >= 10             →  播放音效 + 切换到第二关
```

积木更适合"教学演示"，事件表更适合"做游戏"。

---

## 7. 结论

| 问题 | 答案 |
|---|---|
| 丙适合 mini-Godot 目标吗？ | **不适合**（等于自己重写一个 Godot 编辑器） |
| 严格按"简单简洁"，有更合适的吗？ | 有：**B（Godot + 导出插件）** 在"编辑器代码量"上最省；但它把复杂度转移给了你（要学 Godot） |
| 那到底选哪个？ | **分两步**（第 5 节）：现在用丙做 galgame，但**地基和数据模型按通用做**；做第二种类型时再换壳 |
| 无论选哪条路，都必须先做什么？ | **第 3 节的引擎地基升级**（模式 3 → 模式 0/1 + 硬件 OBJ） |
