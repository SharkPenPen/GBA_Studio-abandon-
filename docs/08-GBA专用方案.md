# GBA 专用方案（最终版）

> 2026-10。前提变更：**放弃多平台，只做 GBA**；主界面用**剪视频式时间轴**。
> 本文是当前有效方案，取代 `06` 文档里"跨平台/多目标"的相关部分；
> 时间轴的具体设计见 `07`。

---

## 1. 放弃跨平台之后，砍掉了什么

你说得对：**素材已经缩到 240×160 / 16 位色，本来就给不了 PSP**。
所以为跨平台做的预留全都是白工，可以直接删掉：

| 原计划里的东西 | 处置 |
|---|---|
| 平台抽象层（渲染/音频/输入的统一接口） | ❌ 删掉，直接调 GBA 硬件 |
| "按目标平台重新导出素材"的管线 | ❌ 删掉，只出一套 GBA 格式 |
| 分辨率/色深可配置 | ❌ 删掉，写死 240×160 / BGR555 |
| 通用资源格式（考虑未来兼容） | ❌ 删掉，直接用 GBA 最省事的格式 |
| 音频后端抽象 | ❌ 删掉，就用 4 声道 + 2 路 DMA |
| 多目标构建（GBA/PC/其他） | 🔧 保留一半：**PC 只用于预览，不做出货版本** |

**收益**：引擎代码约少 30%，资源格式能压到最紧，调试链路短一半。

> 一条建议：**原始大图（1920×1080 那些）别删**。万一将来真要做别的平台，
> 正确做法是从原图重新导出一套，而不是拿缩小过的去放大。留着的成本只是硬盘。

## 2. 没变的三件事（很重要）

### 2.1 GBA 端和 PC 预览仍然共用同一份 C 代码

这和跨平台无关 —— 它解决的是**"预览里好好的，烧进 ROM 就不对"**这个问题。

```
        vm.c（字节码 VM） + render.c（240×160 渲染）
                        │
            ┌───────────┴───────────┐
      arm-none-eabi-gcc          mingw-gcc
            │                       │
      ┌─────▼─────┐          ┌──────▼───────┐
      │  GBA ROM  │          │  PC 预览播放器 │
      └───────────┘          └──────────────┘
              像素一致、行为一致
```

PC 播放器读的是**同一个编译产物**（打进 ROM 的那份包），
所以预览看到的字、立绘位置、抖动淡入，就是实机上的样子。

### 2.2 时间轴界面（`07` 文档）

轨道、片段、波形、播放头、吸附对齐 —— 照剪视频那套做。
混合时间制（等按键 / 等语音 / 定时）解决"galgame 的时间要等玩家"。

### 2.3 还是需要一个 Windows C 编译器

因为第 2.1 条：PC 播放器要用 C 编。本机没有，但 6 个渠道实测可达，
推荐 **MSYS2 清华镜像 + `pacman -S mingw-w64-x86_64-gcc`**（约 500MB，全程国内网络）。

## 3. 技术栈决策：全 C 的理由还剩几条？

你原本给"全 C"三条理由，现在逐条看：

| 理由 | 放弃跨平台后还成立吗 |
|---|---|
| ① 移植到别的老平台（PSP 等） | ❌ **已放弃**，这条没了 |
| ② 工具能在老电脑上跑 / U 盘免安装 | ⚠️ 还成立，但你的 PC 是 Ryzen 9，实际影响小 |
| ③ 只维护一种语言 | ⚠️ 还成立，但代码是我在写，且工程本来就 Python+C+PS 混合 |

**所以现在的取舍变成了**：

- 如果你**在意 ②③**（便携、单语言、极小体积）→ 走全 C
- 如果**更想快点用上工具、界面好看** → 编辑器用 Python + Qt，C 只做内核

两种我都给了具体数字，见下。

## 4. 三条可选路线

| | **甲：全 C + Win32 API** | **甲′：全 C + GTK**（推荐给"要 C"的你） | **乙：C 内核 + Python/Qt 编辑器** |
|---|---|---|---|
| 语言 | 纯 C | 纯 C（GTK 本身就是 C 写的） | C（内核）+ Python（界面） |
| 界面控件 | 系统自带通用控件，其余全自绘 | **专业控件齐全**（面板/表格/树/对话框） | 最专业（Qt） |
| 时间轴画布 | GDI 自绘 | Cairo 自绘 | QGraphicsView |
| 界面观感 | 朴素 | 良好（可做深色主题） | 最好 |
| exe 体积 | **1~2 MB** | 约 40 MB（带 DLL） | 150~250 MB |
| 启动 | 瞬间 | 1 秒内 | 3~5 秒 |
| 能在老 Windows 跑 | ✅ XP 起 | ⚠️ Win7 起 | ❌ |
| 我的开发量 | **最大**（约 2×） | 中（约 1.3×） | **最小**（1×） |
| 拿到能用的版本 | 最慢 | 中 | **最快** |

**甲′ 说明**：GTK 是纯 C 的界面库，MSYS2 里一条命令就能装
（`pacman -S mingw-w64-x86_64-gtk3`，走清华镜像 ✓）。
它给的是真控件而不是手搓窗口，所以"全 C"和"界面不难看"可以兼得 ——
这是三条路里唯一兼顾两者的。

## 5. 我的推荐

**推荐 乙（C 内核 + Qt 编辑器）**，理由：

1. **时间轴是这个工具的灵魂**，它涉及大量精细交互（拖拽、吸附、缩放、
   波形、多选、撤销）。用 Qt 我能做得又快又好；用 C 手搓同样的东西要多花一倍时间，且容易糙。
2. **最关键的技术优势（预览=实机）不受影响** —— 它是靠 C 内核实现的，与编辑器语言无关。
3. 你剩下的两条理由（便携、单语言）**收益不足以抵消开发量差距**：
   - 体积：你硬盘上光工具链就 1.4 GB，200 MB 不是问题
   - 单语言：工程本来就是 Python + C + PowerShell 混合，多一层界面语言不改变性质
4. **更快拿到能用的东西** —— 你可以早点开始真正做游戏，而不是等我造工具。

**但如果你就是想要全 C**：那选 **甲′（GTK）**，不要选甲（Win32）。
甲 的体积优势（1MB vs 40MB）换来的是明显更糙的界面和更长的开发时间，不划算。

## 6. 架构（推荐路线 乙）

```
┌────────────── 编辑器（Python + Qt）──────────────┐
│  素材库      预览监视器        属性             │
│  ┌──────┐   ┌──────────┐    ┌──────────────┐    │
│  │背景   │   │          │    │ 角色  [魔女▾] │    │
│  │立绘   │   │ 240×160  │    │ 内容  [……    ]│    │
│  │音乐   │   │ 由播放器  │    │ 语音  [自动▾] │    │
│  │语音   │   │ 实时绘制  │    │ 推进  [按键▾] │    │
│  │角色表 │   └──────────┘    └──────────────┘    │
│  └──────┘                                        │
│  时间轴（多轨道 + 波形 + 播放头 + 吸附）           │
│  积木逻辑（变量/条件/分支，按需展开）              │
└────────────┬─────────────────────┬───────────────┘
             │ 编译                 │ 生成预览包
             ▼                      ▼
    ┌────────────────┐    ┌─────────────────────┐
    │ pack.bin       │───▶│ gbaplayer.exe (C)   │ ← 与实机同源
    │ （资源+字节码） │    │ 240×160×3 窗口       │
    └────────┬───────┘    └─────────────────────┘
             │ 嵌入 ROM
             ▼
    ┌────────────────────────────┐
    │ GBA ROM (C + libtonc)      │
    │ 场景对象 │ VM │ 文本 │ 音频 │
    └────────────────────────────┘
```

**关键点**：编译产物 `pack.bin` 只有一份，PC 播放器和 GBA ROM 都读它。
预览和实机是**同一份数据 + 同一份 C 代码**，不可能走样。

## 10. 追加：按「最简单简洁（含代码）」重新取舍

> 2026-10 追加。用户提问："按最简单简洁的思路考虑（包括代码），乙路线还值得选吗？"
> **答：不值得。乙恰恰是三条路里最复杂的。**

### 10.1 乙路线的复杂度清单（之前被"界面最好"掩盖了）

| 复杂度来源 | 具体是什么 |
|---|---|
| 两种语言 | Python（编辑器）+ C（内核） |
| **两套工具链** | Python + pip **和** MSYS2 + mingw-gcc |
| 两套构建 | PyInstaller（打 exe）**和** make/CMake（编 C） |
| **跨语言边界** | 预览要么跨进程（启动播放器 + pack 文件 + 状态同步），要么 ctypes 加载 DLL（窗口句柄、事件循环整合都很别扭） |
| 两套依赖 | Pillow/numpy **和** stb_image/cJSON |
| 两套调试 | Python 调试器 **和** C 调试器 |

**它唯一的好处**是"预览和实机同一份代码" —— 但这个用别的方式能兜底（见 10.4）。
为这一个好处换来上面六条复杂度，**不划算**。

### 10.2 三条路按"简单"重排

| 排名 | 路线 | 语言 | 新增工具链 | 新增下载 | 代码量 | 能用上的时间 |
|---|---|---|---|---|---|---|
| 🥇 | **丙：全 Python（Tkinter）+ 现有 C 引擎** | 2（编辑器 Python / 引擎 C，和现在一样） | **无** | **0** | **最少** | **最快** |
| 🥈 | 甲′：全 C + GTK | 1 | MSYS2 + GTK | 约 500 MB | 多 1.5~2 倍 | 慢 |
| 🥉 | 乙：C 内核 + Qt | 2 | Python + MSYS2 两套 | 约 700 MB | 中 | 中 |

**关键判断：论代码简单，Python 压倒性胜出。**
同一个时间轴逻辑，Python 约 500 行，C 约 1500 行且更容易出错（内存、字符串、状态机）。
你要的是"最简单简洁"，那就是 **丙**。

### 10.3 丙路线为什么够用（两个之前没意识到的点）

**① Tkinter 画时间轴完全够用。**
时间轴的图形元素其实很简单：矩形（片段）、文字、折线（波形）、竖线（播放头）。
都是 Canvas 的原生能力，不需要缩放视口、不需要停靠面板、不需要节点连线 ——
那些才是 Tkinter 的短板，而时间轴方案**恰好不需要它们**。

- 面板：`ttk.PanedWindow` 就是可拖分隔条（时间轴方案只要固定分区）
- 波形：用 Pillow 画成一张图贴上去，比逐个画线快得多
- 拖拽/吸附/命中测试：矩形运算，和现有节点版的做法一样（已验证可行）

**② 现有 `studio/` 就是 Tkinter 写的 —— 是改造，不是重写。**
暗色主题、画布交互、属性面板、日志、打包脚本（PyInstaller）全都能接着用。

### 10.4 预览一致性：用自动化比对兜底（成本很低）

丙路线下预览是第二套实现，理论上会走样。但：

- **静态部分天然一致**：同一份 `.bin` 素材、同一份字体点阵、同一套坐标
- **排版逻辑**只需要把 C 的换行/半角规则移植一次（约 150 行）
- **一致性测试自动化**：我已有 mGBA 截图工具链 ——
  同一段剧情，一边截 ROM 的画面、一边截预览的画面，**逐像素比对**，
  不一致就报警。把它做成一条命令，随时能跑。

这比"维护两套工具链"便宜得多，而且**多了一个安全网**（乙路线也没有这个测试）。

### 10.5 丙路线放弃了什么（诚实清单）

| 放弃 | 影响 | 兜底 |
|---|---|---|
| 预览与实机"同一份代码" | 有走样可能 | 自动化像素比对测试 |
| 编辑器内的音频混音预览 | 预览时听不到 BGM+语音混合 | 先做"单条试听 + 波形看对齐"，混音以后补 |
| 界面精致度 | 不如 Qt | 够用，且与现有 studio 风格统一 |
| 导出 PC 版给别人玩 | 丙路线不提供 | 已放弃多平台，本就无关 |
| 单文件 exe 只有 1~2 MB | 实际是 10~200 MB（装 Qt 的话） | **不装 Qt 就还是 10 MB 左右** ✅ |

**注意最后一条**：如果界面用 Tkinter 而不是 Qt，exe 仍然只有 **10 MB 左右、零外部依赖**
（和现在的 `GBAStudio.exe` 一样）—— 你原本在意的"体积/便携"这一点**也保住了** ✅

### 10.7 结论

**选丙：全 Python（Tkinter 界面）+ 现有 C 引擎。**

唯一让步是"预览是第二套实现"，用自动化像素比对兜底。
