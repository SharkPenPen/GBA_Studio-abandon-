# 05 · 中文 galgame 移植笔记（把 PC 作品搬到 GBA 的实战记录）

这份文档记录的是**真实踩过的坑**，不是理论。每一条都标注了现象、原因、解法，
目的只有一个：下次把别的平台的作品往 GBA 搬时，不用再交一遍学费。

工程结构：

```
scenario/scenario.txt      剧本（纯文本）
tools/build_script.py      剧本 → C 命令数组（同时收集字库字符集）
tools/make_cjk_font.py     按需生成 10x10 中文点阵字库
tools/make_assets.py       图片 → 16 位色位图数据
scripts/build-assets.ps1   一键跑上面三步（顺序不能乱）
source/text.c              中文渲染（UTF-8 解码 + 二分查字库 + 禁则换行）
source/gfx.c               位图原语（DMA 搬运、透明 blit）
source/galgame.c           引擎（状态机 / 对话框 / 立绘 / 选项 / 菜单）
scripts/dev/mgba-drive.ps1 自动化交互测试（发按键 + 截图）
```

## 一、中文字库：整个移植里最难的一环

### 1.1 GBA 完全没有中文支持

没有字库、没有文件系统、没有操作系统。你写 `printf("你好")` 只会往黑洞里输出。
**必须自己做点阵字库**，没有第二条路。

### 1.2 完整 CJK 字库放不下，也不该放

| 方案 | 容量 | 结论 |
|---|---|---|
| 完整 CJK（2 万+ 字）10x10 点阵 | 20000 × 20 B ≈ **400 KB** | 一个游戏用不到 1%，纯浪费 |
| 常用 3500 字 10x10 点阵 | ≈ **70 KB** | 可行，但仍有一半用不到 |
| **按需生成**（本工程做法） | 336 字 ≈ **7.2 KB** | ✅ 最优 |

做法：字符集从三个来源自动合并，保证不漏字也不浪费：

1. `source/assets/scenario_charset.txt` —— 剧本里出现过的字（`build_script.py` 产出）
2. `source/**/*.c` 里字符串字面量中的非 ASCII 字符 —— 界面文字（"开始游戏"等）
3. ASCII 0x20~0x7E + 一批符号（▼▲→←…）

> **扫描 C 源码前必须先剥掉注释**。否则注释里的中文（比如 `/* 这里要"重画整屏" */`）
> 会被字符串正则误当成 UI 文字塞进字库。功能上无害，但字库白白变大 ——
> 实测未剥注释时多收了 113 处。

### 1.3 字号选择：宋体 12px 内嵌点阵 → **缩放到 11px**（本工程默认）

这是本工程最重要的一条美术/技术决定，全部结论都是实测出来的。

**关键事实一：宋体只在 12px 这一档"内嵌点阵字形"。**
中易宋体（SimSun）在字体文件里内嵌了一套手工调过的点阵（Windows 上经典的
"宋体 12px 点阵"）。FreeType 在字号**正好匹配**时会直接取这套点阵，
而不是去缩放轮廓线 —— 于是笔画锐利、没有抗锯齿糊边。

**关键事实二：想更小，要"缩放点阵"，不能"缩小字号"。**
把字号从 12 调到 11，FreeType 就找不到对应的点阵档位了，
只能去缩放轮廓线并加抗锯齿 —— 笔画立刻断裂。
正确做法是：**先用 12px 渲染拿到手工点阵，再把它按面积平均缩到 11px**。
缩放的是手工点阵，不是轮廓线，所以质量差别很大。

**怎么判断有没有用上内嵌点阵：看渲染结果的灰度级数量。**
灰度级 = 2 表示整幅图只有纯黑纯白，这正是"点阵字形"的特征；
上百个灰度级说明是轮廓线缩放 + 抗锯齿（`make_cjk_font.py` 每次都会打印这项检查）。

实测对比（同一句话 18 个字，亮点数=墨迹多少）：

| 做法 | 灰度级 | 平均亮点 | 笔画<20 的字 | 结论 |
|---|---|---|---|---|
| simsun 12px 内嵌点阵 | 2 | 40.4 | 2/18 | ✅ 锐利，但偏大 |
| **12px 点阵面积缩放到 11px** | 2 | 36.4 | 3/18 | ✅ **当前默认**，小一圈仍锐利 |
| simsun 11px 轮廓（阈值 100） | 168 | 18.9 | 9/18 | ❌ 一半字笔画断裂 |
| simsun 11px 轮廓（阈值 70） | 168 | 25.6 | 4/18 | ❌ 细且脏，不能用 |
| simhei 10px 轮廓 | 231 | 30.9 | 5/18 | ⚠ 笔画粘连、复杂字糊成块 |

**和实际 GBA 游戏对比过。** 拿两张 240x160 的原生截图量：
文字是 **12px 字距、11x11 的墨迹**（15 个字横跨 178px）。
"12px 点阵缩到 11px"出来的正是这个尺寸 —— 所以这个做法是有依据的，
不是拍脑袋定的。

**换字号必须同步改布局。** 字号不只是字体参数，它决定：
- 每行能放多少字（11px 汉字 → 一行 18 个）
- 行距（11px 字形配 12px 行距）
- 对话框高度、名字行、▼ 提示的位置

`source/galgame.c` 里的布局常量现在是**推导式**的（框高由行数和行距算出来），
改 `TEXT_LINES` / `LINE_H` 时框高会自动跟着变，但 `TEXT_MAX_PX` 要手工对齐。

**字库里没有的字符会渲染成空白，而且不报任何错** —— 这是最危险的失败模式。
`make_cjk_font.py` 每次都会列出"渲染为空白"的字，看到就要处理。

实测宋体下**不存在**的常用符号：`▶ ◀ ♪`。
（本工程的菜单光标因此用代码画三角形，而不是去求一个字体里没有的字符。）
全角空格 `　` 渲染为空白是正常的（它本来就是空格）。

### 1.4 字库格式、查找与**半角 ASCII**

每个字 11 行，每行一个 `u16`，**最高位是最左边的像素**（bit15 = x0），共 22 字节。

```
font_glyphs[]  N × 11 个 u16
font_index[]   N 个 u32，码点升序
```

查找用**二分**（336 字时约 9 次比较）。不用哈希表：省空间，而且够快。

**半角 ASCII 是个必须处理的问题。** CJK 字体里 ASCII 的步进是汉字的一半
（宋体 12px：汉字 12px、ASCII 6px）。如果按全角宽度排版，
`GBA` 会被撑成三个全角字那么宽，中英混排的界面会很难看。

处理办法很省事：**字形数据仍然按 11x11 的定长格子存**（保持二分查找简单），
但 C 侧对 ASCII 只推进 `FONT_ASCII_W` 像素：

```c
int text_advance(u32 cp) { return (cp < 0x80) ? FONT_ASCII_W : FONT_GLYPH_W; }
```

ASCII 只用格子的左边几列，右边本来就是空的，正好被下一个字覆盖 ——
**不需要任何额外存储结构**。

⚠ **`FONT_ASCII_W` 不能简单写成 `FONT_GLYPH_W / 2`。**
按"格子宽的一半"算是 5 像素，但实测宋体 12px 的 ASCII 墨迹有 6 列宽
（94 个可打印字符里 93 个墨迹到第 5~6 列），缩到 11px 后用 5 列
会砍掉 38 个字符的最后一列。正确做法是**按源字体步进等比缩放**：
`6 × 11/12 ≈ 6`，所以 ASCII 宽度是 6。
这个值由字库工具算出来写进 `include/font_data.h`，C 侧不要写死 ——
否则改字号时两边会脱节。

两个配套细节：
1. **换行按像素算，不能按字数算。** 否则中英混排时换行会过早
   （一行明明还能塞下几个字母）。`text_layout()` 的第二个参数是像素预算。
2. **极少数宽字母的墨迹会超出自己的可用宽度**（源 12px 下只有 `m` 到第 7 列），
   生成脚本会把这类字形整体左移并在日志里列出来。
   收窄 ASCII 宽度会让"被左移"的字符数量暴涨（5 列时是 33 个，6 列时 0 个）——
   这个数字是判断宽度选得对不对的直接信号。

### 1.5 UTF-8 解码要自己写

GBA 上没有标准库帮你做这件事。汉字在 UTF-8 里是 3 字节，
`text_next_cp()` 处理 1~4 字节序列，非法字节跳过并返回 `'?'`。

**注意**：GCC 默认 `-fexec-charset=UTF-8`，所以 C 源码里的中文字符串
在 ROM 里就是 UTF-8 字节，和这套解码器正好对上。
但如果你的编译器/编辑器用了 GBK，就要改解码逻辑 —— 这是个容易忽略的坑。

### 1.6 字数涨上去会怎样

| 剧本规模 | 不同汉字数 | 字库体积（11×11，每字 22 字节） |
|---|---|---|
| 本次测试（约 30 句） | 148 | 3.3 KB |
| 短篇（1 万字） | 约 1500 | 33 KB |
| 中篇（10 万字） | 约 3000 | 66 KB |
| 长篇（50 万字） | 约 4500 | 99 KB |

GBA ROM 最大 32MB，字库不是瓶颈。**真正的瓶颈是屏幕**：
11px 字一行 18 个，对话框 3 行 = **一屏 54 字**。
移植长篇作品时，玩家要点很多次才能读完一段话 —— 这是必须面对的设计约束。
（想一屏放更多字就得缩小字号，但 1.3 节说明了"缩小字号"会让笔画断裂，
这是个没法两全的取舍。）

## 二、美术素材转换

### 2.1 分辨率：1920x1080 → 240x160

**8 倍降采样**，细节必然丢失。要点：
- 用 `LANCZOS` 重采样，比 `BILINEAR` 锐利得多
- 立绘不要按原图尺寸缩放，**先裁到人物包围盒**再缩放，否则人物只占屏幕一角

### 2.2 ⚠ 素材自带 alpha 通道（我踩过，浪费了一轮）

现象：紫发少女的立绘"包围盒"算出来是整幅 1920 宽，缩完变成 240x109 的畸形图。

原因：素材是 **RGBA**，背景是透明的。我用 `convert('RGB')` 之后再去做
"去掉边缘连通的白色"，透明区被转成了黑色垃圾，判断全错。

**正确做法**：先看素材有没有 alpha，有就直接用，别去猜背景色。

```python
if 'A' in im.getbands() and (np.asarray(im.getchannel('A')) < 128).mean() > 0.005:
    rgba = im.convert('RGBA')          # 用文件自带的透明信息
else:
    rgba = cut_background_by_floodfill(im.convert('RGB'))   # 才需要抠底
```

实测本工程 5 张素材**全部**是 RGBA（立绘透明区占 72% / 81%）。

### 2.3 透明色 key 要自动挑，不能写死

模式 3 没有调色板，透明只能靠"某个特定的颜色值"约定。
如果这个颜色正好出现在立绘自己身上，就会被**打穿**。

做法：扫描立绘用到的所有颜色，从候选表里挑一个**没出现过的**：

```python
used = set(np.unique(rgb[opaque]).tolist())
key = next(k for k in KEY_CANDIDATES if k not in used)
```

本次两张立绘都选中了 `0x7C1F`。key 存在资源描述表里，每个立绘各自带一个。

### 2.4 色深与色彩

GBA 是 15 位色（BGR555），每个通道只有 5 位（0~31）：

```
像素 = (r>>3) | ((g>>3)<<5) | ((b>>3)<<10)
```

- 渐变会有明显台阶（天空、海水最容易看出来）
- 屏幕不发光，实机看着比电脑暗
- 想要平滑过渡得用抖动（dither）；模式 3 下没有硬件混合可用

### 2.5 立绘尺寸是性能问题，不只是美术问题

见下一节。

## 三、显示与性能（模式 3 的取舍）

### 3.1 为什么选模式 3

| 模式 | 优劣 | 结论 |
|---|---|---|
| **模式 3**（16bpp 位图，单缓冲） | 直接色，无需调色板管理，背景/立绘各保持原色 | ✅ 本工程用 |
| 模式 4（8bpp + 双缓冲翻页） | 无撕裂，但**背景、立绘、文字要挤进同一个 256 色调色板** | 颜色会明显劣化 |
| 模式 0（tile + 硬件精灵） | 性能最好，立绘是硬件合成的 | 需要图片转 tile 的工具链（本环境缺 grit） |

### 3.2 一帧只有 280,896 个周期

实测关键开销：

| 操作 | 开销 | 说明 |
|---|---|---|
| 整屏清屏（19,200 次 32 位写） | **约 60% 的一帧** | 所以绝不能每帧全屏重画 |
| 整屏 DMA 拷贝 | 一次搬完 19,200 字 | 换背景用，几乎不占 CPU |
| 两张 148px 立绘的软件 blit | **约 4.8 万像素 → 超过一帧预算** | 见 3.4 |
| 一行 18 个汉字（198 个字形行） | 很小 | 可以每帧更新 |

### 3.3 绘制顺序必须和电子束扫描顺序一致

GBA 从上往下一行行显示。写"已经扫描过去"的行，这一帧就看不到，
而下一帧开头又被清屏覆盖 —— 表现为**屏幕上半部分永远显示不出来**。
（这个坑在 [docs/02](02-第一个ROM.md) 里有详细记录。）

**意外的好处**：对话框放在屏幕下方，是性能上最优的选择 ——
电子束最后才扫到它，留给"更新文字"的时间窗口最宽（约 0.7 帧）。
所以每帧更新对话框文字完全安全。

### 3.4 ⚠ 软件 blit 立绘会撕裂（实测抓到了）

**现象**（自动化截图抓到的真实帧）：立绘盖在对话框上面，文字区混进立绘像素。

**原因**：模式 3 没有硬件精灵，立绘是逐像素贴上去的。
两张 148px 高的立绘要写约 4.8 万个像素，超过了"电子束从顶部扫到对话框(y=98)
之前"的时间预算，于是本帧下半部分显示的是"框还没画上去"的中间状态。

**解法（按推荐顺序）**：

1. **把立绘改小** —— 实测从 148px 降到 120px，像素量少约 1/3，撕裂消失，
   而且两个立绘不再互相重叠，构图反而更好。这是最省事的一招。
2. **改用硬件精灵**（模式 0 + OBJ）：立绘由硬件合成，CPU 完全不参与，
   128 个精灵、性能绰绰有余。代价是要接 tile/调色板工具链。
3. **双缓冲**（模式 4/5）：画完再翻页，彻底无撕裂。
   但模式 3 的显存只有一块 240x160x2 = 76,800 字节的画布（96KB 显存装不下第二块），
   所以模式 3 本身**做不到**双缓冲。

### 3.5 立绘的擦除要用"从背景恢复"

立绘叠在背景上。要移动/隐藏立绘时，不能简单填色（会露出色块），
必须从**背景图**把那一块矩形拷回来：

```c
gfx_restore_rect(x, y, w, h);   // 逐行 DMA，从 ROM 里的背景数据恢复
```

注意只恢复到对话框上沿（`y < BOX_Y`）：对话框是不透明的，下半部分本来就该被它盖住。
这样既擦干净了立绘，又不会把对话框一起擦掉。

### 3.6 DMA 是唯一能访问卡带 ROM 的通道

- `DMA3` 是三个通道里**唯一能读卡带 ROM** 的，从 ROM 拷图必须用它
- 固定源模式（`DMA_FILL32`）可以当"整屏填充"用，一行寄存器搞定
- 逐行 DMA 适合矩形恢复：每行一次搬运，比 CPU 循环快得多

（libtonc 没有 DMA 辅助头文件，`tonc_dma.h` 不存在，直接操作
`REG_DMA3SAD/DAD/CNT` + `tonc_memdef.h` 里的 `DMA_CPY32` / `DMA_FILL32`。）

## 四、引擎与交互

### 4.1 对话框布局（踩过的坑）

**第一版把名字牌画在对话框外面**（框上方一块小牌子）。
结果：旁白（说话人为空）时只是"不画名字"，却没擦掉上一句的 —— 
屏幕上一直挂着"魔女"，截图里看得清清楚楚。

**改法**：名字画进对话框**内部**（高亮色）。换句时整个框会重画，旧名字自然被覆盖，
不需要任何额外的擦除逻辑。这就是"让不变量替你做清理"。

### 4.2 长按连发的重复触发

第一次实现"长按 A 快进"时，单次按键和连发逻辑会在**同一帧**各推进一次，
表现为偶尔跳句。

```c
/* 错的：两个分支可能同时成立 */
if (key_is_down(KEY_A)) { s_hold++; if (s_hold > 20 && s_hold % 5 == 0) advance(); }
if (key_hit(KEY_A)) advance();

/* 对的：用 else if 保证一帧只推进一次 */
if (key_hit(KEY_A) || key_hit(KEY_B)) advance();
else if (s_hold > AUTO_START && ((s_hold - AUTO_START) % AUTO_STEP) == 0) advance();
```

### 4.3 中文换行要做"禁则处理"

中文没有空格，只能在字之间断行。但不能乱断：

- **行首**不能是收尾标点：`，。、！？：；）」』…—`
- **行尾**不能是开头标点：`（「『`

处理：本行排满后，如果下一个字是收尾标点，就把本行最后一个字挤到下一行，
让标点留在行尾。实现见 `text_layout()`。

### 4.4 按键语义

| 用法 | 语义 | 适用 |
|---|---|---|
| `key_hit(k)` | 边沿触发（刚按下） | 菜单选择、推进对话、切换开关 |
| `key_is_down(k)` | 电平触发（按住期间） | 长按快进、持续移动 |
| `key_tri_horz()` / `key_tri_vert()` | 三态（-1/0/+1，带自动重复） | 角色移动 |

必须先 `key_poll()`，否则读到的是上一帧的快照。

### 4.5 一屏能放多少字（移植时的容量计算）

```
对话框宽 232px，文字区 18 汉字/行（11px 点阵；ASCII 半角 6px）
3 行 → 一句最多 54 个汉字，一屏 54 字
```

## 五、构建管线与自动化测试（这部分救了整个项目）

### 5.1 剧本要在 PC 上编译，不要写进 C

`scenario/scenario.txt` 是纯文本，`build_script.py` 把它编译成命令数组：

```
bg bg_ocean                     → { CMD_BG, SC_BG_OCEAN, ... }
char left witch                 → { CMD_CHAR, SC_POS_LEFT, SC_CH_WITCH, ... }
say 魔女|海风停了。              → { CMD_SAY, 0,0, "魔女", "海风停了。", ... }
choice 走海岸->route_a|翻悬崖->route_b   → { CMD_CHOICE, ..., "走海岸", "翻悬崖", 目标下标, 目标下标 }
@route_a / jump / end
```

标签在**编译期**解析成命令下标，GBA 上不需要任何字符串查找。
**好处**：改剧情不碰 C 代码；还能顺便自动收集字库字符集。

### 5.2 大块数据用 `.incbin`，不要写成 C 数组

2 张背景 153KB、2 张立绘 63KB。写成 C 数组会产生 1MB 以上的源码，编译极慢。

做法：Python 生成 `.bin` + 一个汇编存根：

```asm
    .section .rodata
    .global gfx_bg_ocean
    .align 2
gfx_bg_ocean:
    .incbin "bg_ocean.bin"
```

**关键点**：`.incbin` 靠 `-I` 找文件（GAS 会在 `-I` 路径里搜索），
所以构建脚本必须把 `source/assets` 加进包含路径，否则汇编失败。

### 5.3 ⚠ 自动化测试：GBA 没有 printf 调试，只能"按键 → 看画面"

这是整个开发中最花时间的部分。逐条记录：

#### (1) 全局按键注入会干扰你正在用的程序

`keybd_event` / `SendInput` 是**系统级**注入：它要求目标窗口处于前台，
一旦你切去用浏览器或聊天工具，按键就打进那个程序里。
**本次开发中真的发生了一次**：截图拍到的是聊天窗口，按键差点发进对话框。

#### (2) 定向消息投递（PostMessage）mGBA 收不到

改成 `PostMessage(hwnd, WM_KEYDOWN, ...)` 只发给模拟器窗口、不需要前台 ——
但**完全无效**。原因：mGBA 的键盘输入走 SDL，SDL 读的是系统级键盘状态，
窗口消息绕不过去。

#### (3) ⚠ mGBA 默认"窗口失焦就暂停"（这个坑卡了很久）

`config.ini` 里 `pause_emulator_when_inactive=1` 是默认值。
所以在后台跑游戏时，**它其实是暂停的**：画面永远停在第一帧，
看起来就像"按键没生效"。

判断方法：**看窗口标题有没有帧率**。标题是 `mGBA - GBA AI DEMO - 0.10.5`
说明暂停了；正常跑会显示 `mGBA - GBA AI DEMO (60.1 fps) - 0.10.5`。

解法：改 `.toolchain\mgba\...\config.ini`：

```ini
[window]
pause_emulator_when_inactive=0
```

#### (4) 键位必须照抄模拟器自己的配置

我凭印象用了 A/S 作为手柄 A/B，结果**全错**。mGBA 的默认映射是：

| 手柄 | 键盘 |
|---|---|
| A | **X** |
| B | **Z** |
| START | 回车 |
| SELECT | 退格 |
| L / R | A / S |

正确来源是 `config.ini` 里的 `[gba.input.QT_K]`。

#### (5) 最终方案：编译期自动演示 + PrintWindow 后台截图

既然输入注入这条路又危险又不可靠，就**让游戏自己按**：

```c
#ifdef GAL_AUTOPLAY
    s_auto_a    = ((s_frame % 120) == 0);      /* 每 2 秒"按"一次 A */
    s_auto_down = ((s_frame % 480) == 60);     /* 每 8 秒"按"一次下 */
#define KEY_HIT(k)  (key_hit(k) || ((k) == KEY_A ? s_auto_a : ...))
#endif
```

```powershell
.\build.ps1 -Clean -OutputName gba_ai_auto -Define GAL_AUTOPLAY   # 测试版，不覆盖正式版
.\scripts\dev\mgba-drive.ps1 -Rom .\gba_ai_auto.gba -Steps "wait:2;shot:t000;wait:4;shot:t004;..."
```

截图用 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` —— 
**不需要窗口在前台，不会打扰你**。
（注意：mGBA 用 OpenGL 渲染时 `PrintWindow` 可能返回黑图，
所以脚本里做了"全黑检测 + 临时切前台 + 把焦点还给你原来的窗口"的回退。）

这个方案一次跑通全程，抓到的问题包括：旁白残留名字牌、立绘撕裂。

#### (6) 子进程必须重定向标准输出

GUI 模拟器如果继承了脚本的输出管道，脚本结束后管道也不关闭，
调用方会一直以为脚本还在运行（表现为"命令挂死不返回"）。
`Start-Process` 时一定要加 `-RedirectStandardOutput` / `-RedirectStandardError`。

#### (7) 别用相对路径传 ROM

`Start-Process` 的参数是按**子进程的工作目录**解析的。
脚本把工作目录设成了 mGBA 自己的目录，相对路径的 ROM 就找不到了 ——
现象是"模拟器起来了但没加载游戏"。传路径前先 `Resolve-Path` 转绝对路径。

## 六、还没做、但移植时必须考虑的功能

| 功能 | 难度 | 要点 |
|---|---|---|
| **存档** | 中 | 要探测卡带存档类型（SRAM 32KB / Flash 64~128KB / EEPROM 512B~8KB），三种访问方式完全不同，不能写死 |
| **音频** | 中 | 4 声道（2 方波+1 波形+1 噪声）+ 2 个 DMA PCM。官方 maxmod 库在当前网络下拿不到，得自己写混音或转 PCM |
| **文字回顾（backlog）** | 低 | 需要保留最近 N 句文本；GBA 的 RAM 只有 288KB，建议只存索引，用时从 ROM 重新取 |
| **转场特效** | 中 | 淡入淡出/溶解。模式 3 下 `BLDCNT` 硬件混合对"位图层的局部区域"无效，只能用抖动或整屏调色板技巧（模式 4 才有调色板可渐变） |
| **立绘表情差分** | 低 | 同一人物的多张脸，注意 RAM/ROM 预算 |
| **图片压缩** | 中 | 背景一张 76.8KB。10 张背景就 768KB。可用 LZ77（BIOS 自带 SWI 解压）或 RLE |
| **竖排文字** | 高 | 中文竖排要另做排版逻辑 |
| **分支/路线管理** | 中 | 本工程的角色/背景状态是隐式维护的，路线复杂后需要显式场景栈 |

### 移植检查清单

搬一部 PC 作品过来时，按这个顺序做：

1. **提取剧本** → 转成本工程的 `scenario.txt` 格式（写个转换脚本）
2. **统计字符集** → 跑 `build_script.py`，看有多少个不同汉字
3. **决定字号** → 汉字数 × 24 字节 = 字库体积；优先试**宋体 12px**（自带内嵌点阵，见 1.3）
4. **转换素材** → 背景缩到 240x160、立绘裁包围盒后缩到 120~130px 高
5. **检查透明** → 素材有没有 alpha？没有才需要抠底
6. **算容量** → 背景数 × 76.8KB + 立绘数 × 30KB + 字库，看 ROM 够不够
7. **算屏幕容量** → 11px 字一屏只有 54 字，长段落要拆分
8. **做自动演示版** → 用它跑完全程截图核对，比手工点快一个数量级
